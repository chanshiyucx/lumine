# 瀑布流优化 v2

## 目标

这一轮先停止继续打补丁，重新审视首页瀑布流的实现方式。

当前最明显的问题不是某一个局部样式，而是刷新首帧会出现以下不符合预期的现象：

- 一开始列数不对，右侧会短暂空出一列
- 有时会先出现整屏的单张 blurhash 图片
- 随后 hydration 完成后，布局又会重新收敛为正确的瀑布流

这些现象说明当前实现存在多条首屏渲染路径，且它们的布局模型并不一致。

## 结论

问题的根因不是 `manifest.json` 缺少尺寸信息。

当前 `manifest` 已经提供了原图和缩略图尺寸，理论上足够支持稳定的瀑布流布局。真正的问题是：

1. 当前项目为了绕过 `masonic` 在 Next SSR 下的限制，额外引入了一条 `StaticPhotoMasonry` 服务端 fallback 路径。
2. 这条 fallback 路径并不使用和最终瀑布流完全相同的布局算法。
3. 因此浏览器首帧看到的并不是“最终布局的静态版本”，而是“另一套临时布局”。

这正是为什么会出现：

- 首帧列数错误
- 首帧空位
- 首帧整屏 blurhash
- hydration 后又恢复正常

也就是说，当前问题的本质不是“尺寸算错”，而是“首帧和最终帧不是同一个组件模型”。

## 对比 Afilmory

### Afilmory 的核心特点

参考 `docs/web` 后，Afilmory 的瀑布流有几个关键特征：

1. 它是一个 SPA，`docs/web/package.json` 中已经明确写了 `Photo gallery SPA`。
2. 它没有在服务端先渲染一套“临时瀑布流”，再在客户端替换成另一套。
3. `MasonryPhotoItem` 总是接收 `width`，并直接用 `width / aspectRatio` 计算高度。
4. blurhash 和 thumbnail 始终处于同一套 item 结构中，而不是依附在不同布局路径下。

换句话说，Afilmory 的流畅感来自于：

- 只有一条渲染路径
- item 的几何尺寸始终明确
- blurhash 只是图片占位层，不负责兜底布局

### 我们当前和 Afilmory 的关键差异

当前项目比 Afilmory 多出来的复杂度主要在这几处：

1. `PhotoMasonry` 中存在 `StaticPhotoMasonry` 和 `PhotoMasonryGrid` 两条路径。
2. 用 `useSyncExternalStore` 在 mounted 前后切换这两条路径。
3. `StaticPhotoMasonry` 依赖 CSS columns。
4. `PhotoMasonryGrid` 依赖 `masonic` 的绝对定位布局。
5. `PhotoCard` 在 fallback 路径下没有明确 `width`，而是在另一条路径下才拿到 `width`。

这意味着当前首页不是一个组件在“渐进增强”，而是两套不同实现之间在切换。

## 为什么会出现整屏 blurhash

整屏 blurhash 不是 blurhash 本身有问题，而是布局路径有问题。

当前 `PhotoThumbnailImage` 的结构本身是正常的：

- 底层 blur 图
- 上层 thumbnail 图

问题出在它被放进了 `StaticPhotoMasonry` 这个临时布局里。

当首帧仍然处于 fallback 路径时，如果浏览器此刻展示的是单列流，或者 column 布局尚未稳定，那么第一张卡片会先以接近整屏宽度的 block 形式出现。由于 blur 图是 `absolute inset-0 h-full w-full object-cover`，视觉上就会像“整屏只有一张 blurhash 图”。

所以这里的错误不是：

- blurhash 太大
- thumbnail 没有尺寸

而是：

- blurhash 被放进了一条不稳定的首帧布局路径中

## 当前代码里不够优雅的部分

这轮分析后，当前实现里最应该收敛的是这些 hack：

1. `StaticPhotoMasonry`
2. `useSyncExternalStore` 的 mounted 切换逻辑
3. 首帧专用的 CSS columns 断点修补
4. `PhotoCard` 同时支持“有 width”和“无 width”两种模式
5. 各种围绕 SSR 首帧的额外测宽和补偿

这些代码单看都能解释，但叠在一起之后，首屏行为就会越来越难预测。

## 建议的重构方向

### 方向一：回到单路径渲染

这是最推荐的方向。

核心原则是：

- 首页瀑布流只保留一套真正的 masonry 实现
- `PhotoCard` 始终依赖明确的 `width`
- blurhash 只做图片占位，不参与布局兜底

也就是说，不再让首页经历“先是 CSS columns，再切到 masonic”的过程。

### 方向二：接受 client-only gallery

如果 `masonic` 在 Next SSR 下天然不适合首屏稳定渲染，那么就不要强行做一套服务端瀑布流 fallback。

更干净的做法是：

- header 和页面壳仍然可以服务端输出
- 瀑布流区域改为 client-only
- hydration 前只显示稳定的页面背景，不显示临时 photo tiles
- hydration 后一次性进入最终瀑布流

这会比当前“双路径切换”更接近 Afilmory 的实际体验。

它的取舍是：

- 首帧不显示错误的 blurhash
- 首帧也不显示一套假的瀑布流
- 页面在 JS ready 后直接进入正确布局

对于这个项目来说，这个取舍是合理的。

### 方向三：简化 item 责任

`PhotoCard` 应该被收敛成单一职责：

- 外层只负责点击、hover 信息和可访问性
- 高宽由上游 masonry 明确传入
- 图片层永远是 `blurhash -> thumbnail`
- 不再显示错误文本 fallback

如果 thumbnail 加载失败，理想表现应当是：

- blurhash 继续保留
- 清晰图不显示
- 不打断布局，也不插入额外的错误 UI

这和 Afilmory 的思路是一致的。

## 实施结果

这一轮已经按上述方向完成重构，重点不是继续修 `fallback`，而是删除它：

1. `PhotoMasonry` 已移除 `StaticPhotoMasonry`
2. `PhotoMasonry` 已移除 `useSyncExternalStore` 的双路径切换
3. 首页瀑布流现在只保留一条 `client-only` 的 `PhotoMasonryGrid` 路径
4. `PhotoCard` 现在必须接收明确的 `width`
5. `PhotoCard` 已移除错误文本 fallback，只保留 `blurhash -> thumbnail`
6. SSR 专用的 static masonry CSS 和 `MASONRY_SSR_WIDTH / MASONRY_SSR_HEIGHT` 也一并删除

当前实际实现是：

- 页面壳仍然正常渲染
- 瀑布流区域不再输出一套临时的错误布局
- 客户端 ready 后一次性进入真正的 masonry

这意味着首页首帧不会再经历：

- CSS columns 临时布局
- hydration 后切换到 `masonic`
- 第一张 blurhash 被放大成整屏

## 最终判断

这次问题的关键不是“某个数字算错了”，而是当前实现偏离了 Afilmory 的基本前提：

- Afilmory 是单路径
- 当前实现是双路径

只要首页还保留两套不同的瀑布流模型，首帧错位、空位、整屏 blurhash 这类问题就会不断以不同形式出现。

这一步已经从“继续修补 fallback”转向了“删除 fallback，收敛成单一路径”。
