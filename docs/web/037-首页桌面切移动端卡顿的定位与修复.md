# 首页桌面切移动端卡顿的定位与修复

- 状态：已实施，用户复测确认改善
- 日期：2026-09-25
- 范围：首页瀑布流在 Chrome DevTools 中从桌面模式切到移动设备模式

## 现象与问题边界

桌面切移动端时，画廊会明显停顿，随后才显示正确的两列；移动端切回桌面则较快。最初怀疑 `ResizeObserver` 的通知、React state 更新或列数重排太慢。参考 Afilmory 的切换视频与实现后，先尝试在列数跨断点时同步提交 React 更新，并减少重复的虚拟列表测量。窗口宽度单独变化的测试有改善，但用户在原来的设备模式切换场景中几乎感觉不到变化，说明这不是主要瓶颈。

关键区别是：DevTools 的设备模式除了改变视口宽度，还会改变 `(hover: none) and (pointer: coarse)` 的匹配结果。[`PageScrollArea`](../../web/components/scroll-area/scroll-area.tsx)据此将滚动元素从 Radix viewport 切到 `document.body`；[对应 CSS](../../web/styles/globals.css)也让 Radix viewport 在触摸模式下改为随内容增长。仅缩窄浏览器窗口不会触发完整的滚动模式切换。

## 定位过程

1. **隔离宽度变化。**只改变视口宽度时，列数最终能正确重排；先前针对 `ResizeObserver` 和 React 提交的调整只缩短了这一条路径，没有解释用户录屏里的明显停顿。
2. **隔离触摸模式。**保持桌面宽度约 1179px，只切换触摸/指针模拟。切入触摸模式时，用 `MutationObserver` 观察 `ul[aria-label="Photos"]`，记录到虚拟列表先挂载全部 **458** 张照片，再回落到约 **36** 张。这个实验不依赖移动端列数变化，因而把主要问题定位到滚动视口测量，而不是两列布局算法。
3. **核对测量来源。**TanStack Virtual 默认的 `observeElementRect` 会立即读取滚动元素尺寸，之后由 `ResizeObserver` 更新。过渡期间，旧的 Radix viewport 会短暂随整页内容增长，其高度被当作“可见视口高度”传给虚拟器，于是虚拟器判断所有照片都在可挂载范围内。大量卡片及图片节点的创建占用了主线程。
4. **验证过渡节点。**第一次只针对 `document.body` 限制高度，仍出现全量挂载；当时报告异常高度的是 React 切换滚动元素之前的**旧 Radix viewport**。因此限制必须作用于两种滚动元素的共同测量入口。

在本地 Chrome 开发环境的隔离触摸切换中，修复前记录到约 2.1–2.5s 的主线程任务时间，其中脚本时间约 1.75–2.1s。这些数字用于确认工作量来源，不作为跨设备或生产构建的性能承诺。反向切换时，Radix viewport 回到固定的视口高度，不会经历这次整页高度被误当作视口的过程；这解释了反向切换更快的体感。

## 与 Afilmory 的对照

Afilmory 的主页面在移动端直接提供 `document.body` 作为滚动元素，桌面端才渲染固定高度的 `ScrollArea`；它的 Masonic 包装层还把 `window.innerHeight` 显式作为虚拟列表高度。这个实现说明虚拟列表应按浏览器视口大小决定挂载范围，而不能把过渡期间的整页内容高度当作视口。两边使用的瀑布流和滚动容器结构不同，因此没有照搬 Afilmory 的组件组织。

## 最终改动

在 [首页瀑布流](../../web/components/gallery/photo-masonry.tsx)为 TanStack Virtual 提供一层 `observeElementRect` 包装：保留库的尺寸观察，仅将上报高度限制为 `document.documentElement.clientHeight` 与原始高度中的较小值。正常较小的滚动容器仍使用自身高度；触摸模式切换时即便旧 Radix viewport 短暂变成整页高，也不会让虚拟器挂载整份照片列表。

```ts
const observeScrollRect: typeof observeElementRect = (
  virtualizer,
  onChange,
) => {
  return observeElementRect(virtualizer, (rect) => {
    const viewportHeight =
      virtualizer.scrollElement?.ownerDocument.documentElement.clientHeight;
    onChange({
      ...rect,
      height: Math.min(rect.height, viewportHeight ?? rect.height),
    });
  });
};
```

此前尝试的 `flushSync` 与额外测量缓存已撤回。最终只保留这一处测量边界修正，没有增加第二套布局状态或滚动监听。`ResizeObserver` 仍负责容器宽度与列数变化；React state 更新和正常的两列重排仍按原有逻辑执行。

## 验证结果

- 相同的隔离触摸切换中，修复后列表保持约 36 个可见及预渲染项，没有再次出现 458 项的峰值；记录的主线程任务约 150ms。
- 在约 1179 × 963 桌面视口切到 393 × 852 移动视口并启用触摸模拟后，最终为两列、约 22 个挂载项；该次主线程任务约 194ms。反向切换也正常。
- 在移动端将页面滚动到约 1200px 后，虚拟项索引从首批照片更新到后续照片，说明高度限制没有阻断正常滚动虚拟化。
- `pnpm exec eslint components/gallery/photo-masonry.tsx`、`pnpm exec tsc --noEmit`、`git diff --check` 均通过。用户按原切换方式复测，确认卡顿问题已消失。

这些测量来自本地开发环境的具体图库与 Chrome 会话，绝对耗时会随照片数量、设备和浏览器状态变化。诊断中可重复的关键证据是“切入触摸模式时曾全量挂载，修复后不再全量挂载”。

## 全链路复核：为什么保留测量边界

2026-09-25 再次沿首页管线检查：服务端读取、校验并排序照片清单；`PhotoGallery` 在客户端连接滚动元素和 Viewer；`useMasonryLayout` 通过容器宽度计算列数与列宽；TanStack Virtual 根据可见高度、照片比例和每列 3 项 overscan 决定挂载范围；图片组件只为挂载项创建缩略图和占位图。触摸切换中的全量挂载发生在**滚动元素高度进入虚拟器**这一环，清单处理、列数查找和图片加载策略不是这次异常的起点。

还试过一个更靠近滚动容器的方案：移除 CSS 媒体查询，让 Radix 的移动端样式与 `document.body` 的选择由同一次 React 更新决定，同时去掉虚拟器的高度上限。桌面到移动端切换确实不再全量挂载；但在移动端首次打开相册页时，先观察到固定高度的桌面滚动容器，客户端接管后才切为整页滚动。同一次导航中，`body.scrollHeight` 从 852px 变到 7637px；这个数值也受页面内容加载影响，不能全部归因于滚动样式。由于 [`PageScrollArea`](../../web/components/scroll-area/scroll-area.tsx)包裹所有页面，样式切换移到首屏并不比现有方案稳妥，因此撤回。

当前实现保留了 CSS 在首帧按设备模式生效，并使用 TanStack Virtual 正式支持的 `observeElementRect` 扩展点限定**可见高度的上界**。即使某个滚动元素的盒子在过渡期达到整页高度，屏幕一次也看不到超过根视口高度的内容；对正常小于根视口的滚动区域，原始测量值保持不变。这是虚拟列表的输入契约，不是用定时器或跳过某次异常通知来掩盖卡顿。

另一个可选架构是所有设备都使用 `body` 滚动，彻底消除滚动元素切换；但它会改变桌面端的 Radix 滚动条及全站滚动行为，还涉及 Viewer 滚动锁定和路由滚动恢复。当前没有证据显示这些改动能比测量边界带来更多用户可见收益，因此没有扩大改动范围。
