# 首页图片链路与瀑布流更新边界清理

- 状态：已实施，待人工视觉回归
- 日期：2026-09-25
- 范围：首页瀑布流、共用缩略图与 ThumbHash，以及 Viewer 回调引用的复核

## 背景与取舍

[此前的切回标签页诊断](032-首页切回标签闪烁的定位与缩略图尺寸策略.md)在闪动复现时没有记录到首页 React commit、DOM 变化或滚动变化，因此这次清理不声称能修复浏览器恢复页面时的图片绘制问题。目标是消除已经能从代码确认的无效计算、无用接口和不必要的更新，同时保持 600px 缩略图、瀑布流布局及卡片视觉设计。

对照 `tmp/afilmory`：它的瀑布流卡片使用固定的 `loading="lazy"`，ThumbHash 只生成图片 URL；其 Masonic 实现仍有位置测量和更多卡片状态。这里只借鉴可验证的简化点，不替换现有虚拟列表或图片组件。

## 实施内容

1. [Viewer 控制器](../../web/components/viewer/hooks/use-viewer-controller.ts)的照片 slug 索引和 `open` 回调曾被手动包上 `useMemo` / `useCallback`。复核发现项目已启用 React Compiler，生产构建也确实为这个 hook 生成了按 `photos` 缓存索引和回调的代码；因此撤回手动 memoization，避免保留一套与编译器重复的依赖管理。Viewer 的行为不变。
2. [ThumbHash 数据 URL](../../web/lib/thumbhash.ts)只解码实际使用的 `dataUrl`，移除了全项目无人读取的平均色计算和 `ThumbHashAsset` 结构。保留 128 项 LRU 缓存，避免虚拟卡片反复挂载时重复解码。组件的占位图内容不变。
3. [ThumbnailImage](../../web/components/image/thumbnail-image.tsx)删除没有调用方使用的 `alt`、`fetchPriority`、`loadImage`、`onLoad` 和 `onError` 参数；[ThumbHashImage](../../web/components/image/thumbhash-image.tsx)只接收现有调用方需要的 `thumbHash`、`placeholderSrc` 和 `className`。真实使用的 `fit`、`loading`、`scaleOnHover` 均保留。两个组件继续使用 Next `<Image>`，原有 `decoding` 与 `unoptimized` 行为不变。
4. [首页瀑布流](../../web/components/gallery/photo-masonry.tsx)将 `loading` 固定为前 `3 × 列数` 张照片 `eager`、其余 `lazy`，删除按当前视口交集反复计算 `eager/lazy` 的函数。这个序号范围只是首批照片的简单上限，**不保证覆盖整个首屏**；后续进入视口的图片交给浏览器原生 lazy 加载。滚动时同一张卡片不再因为跨越视口边界而改写 `loading` 属性。列数在响应式断点变化时，首批范围仍会相应变化。

虚拟列表的 overscan 仍为每列 3 项；它控制挂载范围，与图片的 `loading` 属性职责不同。卡片展开信息的 140px 门槛、hover 过渡和毛玻璃效果均未改动。

## 验证与人工回归

`pnpm type-check`、`pnpm lint`、Prettier 检查、`git diff --check` 以及在 Node 24 下的 `pnpm build` 均通过。`pnpm test` 成功退出，但当前发现 0 个测试用例，不能把它视作交互验证。

人工回归重点：Chrome 首页首屏图片出现速度、滚动到较深位置时图片加载、浏览器恢复滚动位置后图片加载、Viewer 打开与关闭、相册封面和 Viewer 缩略图栏，以及反复切换浏览器标签页时的视觉稳定性。若首屏图片出现明显延迟，应比较固定 eager 数量和浏览器实际请求时序，再调整该范围；仅凭本次代码精简不能推断视觉性能已经改善。
