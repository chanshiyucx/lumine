# 首页切回标签闪烁的定位与缩略图尺寸策略

- 日期：2026-09-24
- 范围：首页照片瀑布流。Viewer 底部缩略图栏的历史排查见 [031-预览切回时虚拟列表稳定性优化.md](./031-预览切回时虚拟列表稳定性优化.md)，不能把两处闪烁直接视为同一个问题。
- 结论：在这批照片和当前布局下，首页直接显示 960px 宽的缩略图会在浏览器标签页恢复时闪烁；显示同一批照片的 600px WebP 则不闪。600px JPEG 也不闪，说明关键变量是显示图片的像素尺寸，而不是 WebP 格式。

## 现象与排查过程

生产构建运行在 `127.0.0.1:3001` 时，首页从其他标签页切回来会短暂闪一下。去掉 Header 后仍可复现；将瀑布流从 `@tanstack/react-virtual` 换成 Masonic 后仍可复现。因此 Header、开发模式和某一个虚拟列表库都不是这个现象的必要条件。

参考项目 Afilmory 的图片构建代码把缩略图目标宽度设为 600px、格式设为 JPEG；本项目的 pipeline 配置是 960px WebP。这个对比指向图片资源，但单凭两边配置不同，尚不能判定尺寸、格式还是浏览器绘制效果起作用。先前依据合成层数量推断的“GPU 着色器雪崩”也没有得到直接证据。

临时诊断在生产页记录了切回前后的 React commit、组件挂载、DOM 变更、滚动、尺寸和图片状态。在多次已复现的切回中，只有 `visibilitychange` 和 `focus` 事件；没有瀑布流 React commit、卡片节点增删、属性变化、滚动或尺寸变化。记录中的 50 张卡片、100 个图片节点在切回前后保持不变，图片已加载。这个结果排除了“切回来重新渲染或虚拟列表把 DOM 清空”作为本次首页闪烁的直接原因，但 `img.complete` 不能证明浏览器仍保留着图片的解码/合成缓存。

随后在相同生产页逐项缩小渲染内容。下面只列出确认探针已生效后的人工复测结果：

| 对照 | 结果 | 能说明什么 |
| --- | --- | --- |
| 保留原尺寸照片与瀑布流，隐藏 ThumbHash、文字遮罩和 hover 效果 | 仍闪 | 这些装饰效果不是必要触发条件 |
| 保留相同卡片与滚动容器，只显示纯色块、不显示照片 | 不闪 | 闪烁依赖照片像素的绘制 |
| 同一批照片改为 600px JPEG | 不闪 | 缩小图片有效 |
| 同一批照片改为 600px WebP | 不闪 | 不必从 WebP 改成 JPEG |
| 普通首页通过 Next 图片接口获取 600px WebP | 不闪 | 当前修复路径有效 |

当时首页首批 50 张 960px WebP 的编码文件合计约 8.3 MiB；按宽高各像素以 4 字节 RGBA 展开，像素量约等于 120 MiB。等比例缩到 600px 后约为 47 MiB。这只是从图片尺寸计算的**解码像素量估算**，不是 Chrome 实测的 GPU 显存，也不能据此断言具体发生了纹理回收、着色器重编译或某一个合成器错误。可以确定的是：缩小同一批照片后，人工复测的闪烁消失了。

## 当前修复

瀑布流已恢复为 `@tanstack/react-virtual`。首页卡片在 [photo-masonry-item.tsx](../../web/components/gallery/photo-masonry-item.tsx) 中把 manifest 的缩略图 URL 指向 `/_next/image?url=…&w=600&q=75`；[next.config.ts](../../web/next.config.ts) 只允许媒体源 `/thumbnails/**` 进入图片优化接口，并把 600 加入允许的宽度。共用的 `ThumbnailImage` 仍使用 `unoptimized`，因此它不会再把这个 600px 地址交给 `<Image>` 生成另一套宽度；实际缩放发生在所指定的 Next 图片接口。

修复限制在首页卡片的图片来源，没有修改瀑布流测量、滚动和虚拟化逻辑。诊断接口、探针样式和临时测试图片已删除。生产构建、类型检查、lint 与图片接口响应均通过；标签页切换的视觉结果由用户人工复测确认，代理没有再次使用浏览器测试。

## 是否改由 pipeline 生成图片

**长期优先方案：由 pipeline 预生成单一 600px WebP，首页和 Viewer 的过渡预览共用同一个 URL；Viewer 再渐进加载现有原图。** 这样首页不必在请求时依赖 Next 把 960px 缩到 600px；Viewer 打开已在首页加载的照片时，也不必为了过渡图再请求另一张 960px WebP。两种尺寸是两个不同的缓存资源，即使只多请求当前打开的一张，也会增加传输、解码和缓存占用；不能仅因为 960px 过渡图可能更清晰就默认生成两档。

本地参考项目 Afilmory 的构建代码只生成一张 600px **JPEG** 缩略图（并非 WebP）；[瀑布流卡片](../../tmp/afilmory/apps/web/src/modules/gallery/MasonryPhotoItem.tsx)和 [Viewer](../../tmp/afilmory/apps/web/src/modules/viewer/PhotoViewer.tsx)共用 `thumbnailUrl`，Viewer 另加载 `originalUrl`。这支持“一档缩略图 + 原图”的资源分层，但不保证本项目 600px 过渡图在所有屏幕上的视觉质量。

当前 Web 工作树的 [Viewer 主预览](../../web/components/viewer/progressive-photo.tsx)和底部缩略图栏也指向与首页相同的 600px Next 图片 URL；[共享转场预览](../../web/components/viewer/transition/shared-photo-transition-preview.tsx)仍直接读取 manifest 的 960px `photo.thumbnail.url`。因此在 pipeline 迁移前，不能声称当前所有 Viewer 路径已经只加载 600px。若 pipeline 将唯一的 `thumbnail` 迁到 600px，这些引用会自然收敛到同一静态资源；短暂放大时可能比 960px 模糊，随后由原图接替。社媒图生成也读取 `thumbnail.url`，需要检查其输出清晰度。

迁移单尺寸方案时需要同步处理：

1. 让 pipeline 生成 600px WebP，并给衍生图规格加入缓存失效条件或使用版本化文件路径。目前 [pipeline 的复用判定](../../pipeline/src/build.rs)只检查源文件大小、修改时间、旧 manifest 路径与输出文件是否存在；单改 `thumbnail_width` 不会重建已有 960px 缩略图。
2. 确保新文件、manifest 与 CDN 缓存按顺序发布，旧 manifest 在迁移期间继续走现有 Next 600px 图片接口。等全部资源可用，再让首页和 Viewer 使用 manifest 的同一 600px URL，移除临时的 Next 缩放入口。
3. 检查 Viewer 过渡、共享转场、底部缩略图和社媒图的清晰度，同时确认首页切回标签仍不闪。如果 600px 在实际 Viewer 使用中明显不足，再考虑增加独立的大图预览尺寸，并量化每次打开的额外请求和解码成本。原图已承担最终全屏画质，不应仅凭理论上的模糊风险默认保留第二档 WebP。
