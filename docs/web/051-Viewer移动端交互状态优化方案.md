# Viewer 移动端交互状态优化方案

- 日期：2026-09-30
- 状态：已收缩多指保护，移除额外的导航／面板锁；当前实施与验证见第 22 节
- 来源：`050-Viewer与Afilmory设计对比分析.md` 中的第一优先级建议
- 范围：窄屏 viewer 的纵向手势、横向切图、信息抽屉与隐藏控件的交互一致性
- 约束：保留 img、现有 Swiper 与缩放库，不新增全局状态库或通用手势协调框架
- 验证状态：源码、静态检查、浏览器键盘／焦点及 Chrome 原生触摸模拟已验证；未进行真实设备运行验证

## 1. 选择这个优化点的理由

本轮优先解决“界面呈现的状态”和“实际允许操作的状态”不一致。该问题直接涉及切图、查看信息、关闭等高频动作，无需增加产品功能，也无需改变图片渲染链路。

当前 `infoOpen` 同时被用于面板开关和切图限制，但它实际只表达抽屉的吸附目标。手指拖动期间、目标已关闭但抽屉尚未离场期间，以及下拉回弹期间，并没有对应的明确操作限制。

优化后的核心契约：纵向交互占用图片舞台时暂停切图；抽屉离场之前不恢复舞台控件；不可见的控件不可操作；双指缩放不触发单指关闭。

## 2. 实施前现状与证据

本节保留设计时的源码分析，描述的是实施前行为；最终实现及运行证据见第 11 节。

### 2.1 抽屉目标与过程混用

`hooks/use-mobile-viewer-interactions.ts` 中：

- `settleInspector(open)` 修改 `infoOpen`，并启动 `inspectorProgress` 动画。
- 手指上滑时直接修改 `inspectorProgress`，没有同步修改 `infoOpen`。
- 关闭时 `infoOpen` 立即变为 false，抽屉仍需完成约 280ms 的收起动画。
- 下拉未达到关闭条件时，图片仍需回弹，但没有显式的回弹占用状态。

`viewer.tsx` 当前传给轮播：

```tsx
isSwipeDisabled={isMobile && mobile.infoOpen}
```

因此上滑初期和收起末期无法仅靠此条件准确描述允许切图的时机。

### 2.2 透明度与可交互条件分离

抽屉进度达到 1 时，移动端工具栏的视觉透明度约为 0.08，缩略图透明度为 0。但 `ViewerToolbar` 和 `ViewerThumbnailRail` 的交互条件仍是：

```tsx
const isInteractive = isVisible && phase === "open";
```

这里的 `isVisible` 来自进场 reveal，并不是抽屉状态。透明度不会自动禁用点击、焦点和辅助技术访问。抽屉覆盖可能挡住部分区域，但不能作为控件自身的交互契约。

### 2.3 多指与取消需要显式处理

当前纵向 drag 回调主要依据 `enabled`、`isZoomed` 和 `closingRef` 返回，没有显式处理 TouchEvent 的多指状态及原生取消事件。

仅等待 `isZoomed` 变化不足以描述从 1x 开始捏合的最初阶段。对当前手势中途加入第二根手指，应放弃纵向操作，并且不能在手指数量重新变为 1 时接着执行下拉关闭。

本地 `@use-gesture/core@10.3.1` 的 `DragEngine` 把设备 cancel 事件也绑定到 `pointerUp`。因此业务层需要区分正常释放与 `touchcancel` / `pointercancel`，不能假设库一定替业务屏蔽关闭判定。

### 2.4 不把风险推断当成已复现故障

本地 Swiper 14.2.0 已根据滑动角度区分横向切图和纵向滚动；`@use-gesture` 的 `axis: 'lock'` 也已有方向锁定。不能据此宣称现有实现必然同时切图和打开抽屉。

缺失的是业务层统一的占用与恢复规则，尤其是回弹、收起、取消和多指接续。斜向竞争的实际表现需运行验收。

## 3. 范围和兼容约束

沿用 `040-预览布局与触摸交互边界.md`：

- `isMobile` 只表示小于 1024px 的窄屏布局，不代表输入设备类型。
- 宽屏 iPad 仍允许触摸左右切图；宽屏侧栏打开不限制轮播。
- 未放大时单指横滑交给 Swiper，放大后单指交给图片平移。
- 移动端抽屉目标在跨断点时保留，桌面侧栏状态独立。
- 保留现有手势阈值、弹簧、缩放与关闭投影，不在这一轮重新调手感。
- Escape 保留当前关闭 viewer 的语义；只单独限制左右键，不引入新的 Escape 层级。
- 保留原图加载延迟、Blob 生命周期、进场 reveal、分享弹窗退出期间的隔离，以及地图实例复用。

本轮仅调整交互许可与焦点，不增加标题、关闭按钮等可见元素，不改变工具栏尺寸。沿用已有抽屉把手。首次手势提示、悬浮预览、三段缩放、缓存、抽屉内容区域拖拽关闭均不在本轮范围。

## 4. 状态设计

### 4.1 三类事实分别表达

| 事实                       | 表达                          | 归属        |
| -------------------------- | ----------------------------- | ----------- |
| 抽屉要打开还是关闭         | `infoOpen`                    | 移动端 hook |
| 抽屉当前呈现位置           | `inspectorProgress`，保持私有 | 移动端 hook |
| 舞台当前是否由纵向交互占用 | 内部 `activity`               | 移动端 hook |

内部 activity 使用一个小的枚举，避免多个布尔量产生不合法组合：

```ts
type MobileStageActivity = "idle" | "vertical" | "settling" | "dismissing";
```

- `idle`：没有纵向拖动、回弹或甩出。抽屉仍可能处于打开状态。
- `vertical`：已锁定为纵向的单指拖动。
- `settling`：抽屉吸附或图片回弹尚未完成。
- `dismissing`：已决定关闭，正在甩出并等待投影交接。

这些状态留在 hook 的 Implementation 中，调用方不需要理解活动枚举或进度阈值。

### 4.2 对外输出操作结果

hook 保留 `infoOpen`、`settleInspector`、`bindStage` 和已有视觉 MotionValue，增加以下语义输出：

```ts
{
  isStageBlocked: boolean;
  stageBlocked: MotionValue<boolean>;
  isInspectorInteractive: boolean;
}
```

`stageBlocked` 是同一个离散阻塞事实的同步通知通道；`isStageBlocked` 是它供 React 渲染使用的镜像，不是第二个可独立修改的状态。实现只在布尔值发生变化时更新 React，不能每帧写 state。

两个输出通道的目的：

- React 镜像用于按钮、inert、aria、键盘与选图入口。
- 同步 MotionValue 订阅用于 Swiper 实例的 `allowTouchMove`，避免只靠 `setState → render → effect` 才限制后续触摸事件。

这个 Interface 只多暴露一个需要同步消费的事实；不把 `inspectorProgress`、activity 或逐项控件策略传给调用方。同步通道用于后续事件的即时限制，不能未经验证假定 effect 与触摸事件同步。

### 4.3 阻塞与内容交互规则

在窄屏可交互模式下：

```ts
stageBlocked = activity !== "idle" || infoOpen || isMultiTouchSequence;

inspectorInteractive =
  infoOpen && !isZoomed && activity !== "vertical" && activity !== "dismissing";
```

阻塞由 `settling` 保持到有效完成回调，抽屉和舞台回弹在尾段都保持一致。所有进度变更都已有对应的 activity 或保留目标，因此不再额外订阅连续进度来推导阻塞；0.02 阈值只用于已有手势的起点／释放判定。

`isMultiTouchSequence` 是 hook 内部的本次触摸序列标记。多指加入后保持阻塞，直到所有手指离开或序列取消，避免缩放尚未上报 isZoomed 时 Swiper 接管；触摸结束后不再因为这个标记限制缩略图或工具栏。

打开吸附过程中允许已显示的抽屉内容和关闭入口操作；纵向跟手拖动时禁用抽屉内容。关闭目标设为 false 后立即禁用内容，但继续阻塞舞台直到动画结束。

## 5. 输入处理和动画生命周期

### 5.1 单指方向归属

1. 从 button、链接、表单或明确标记的交互元素开始，继续忽略纵向拖动。
2. 未过阈值或尚未锁轴时不占用舞台，不让轻点和双击进入纵向 activity。
3. 锁为 x 时交给 Swiper，本次触摸序列不改做纵向操作。
4. 锁为 y 且单指时进入 `vertical`，同步通知舞台阻塞，沿用当前进度和下拉计算。
5. 正常松手后使用已有距离／速度判定：打开或关闭抽屉进入 `settling`；回弹进入 `settling`；达到关闭条件进入 `dismissing`。

同步修改 `allowTouchMove` 能限制后续事件，不能倒推它一定能抢在当前事件的 Swiper listener 之前执行。首个方向判定仍依赖两边已有锁轴／角度逻辑，必须用斜向手势验收。如果发生首次事件漂移，修复集中在 PhotoCarousel 的触摸适配处，通过公开接口恢复当前索引，不操作 Swiper 私有 touch state，也不禁用整个图片层的触摸事件。

### 5.2 多指、取消和缩放

- 第二根手指加入时，先同步设置多指序列标记，将本次 GestureMemo 标为忽略，再取消纵向 drag。取消回调不能再进入正常释放判定。
- 已产生的抽屉／下拉偏移吸附回合法目标，本次触摸序列直到全部手指释放都不重新接管纵向动作。
- 保留图片层的 pinch 事件，不全局 `stopPropagation` 或 `preventDefault` 来屏蔽多指输入。
- 原生 `touchcancel` / `pointercancel` 只执行回弹和清理，绝不调用关闭判定。
- 窄屏图片进入放大状态时取消纵向动作并收起抽屉；缩放和平移沿用图片模块，恢复适应屏幕后重新允许新的单指手势。
- 第二根手指落在舞台的哪个子元素上、库是否重新启动 drag，需真实触摸验证。使用舞台已有 TouchEvent 入口或捕获入口维护本次触摸序列的忽略标记，不能仅靠最后一个 drag 回调猜测。

### 5.3 动画完成与中断

每次吸附、回弹和甩出分配本地动画编号。启动新动作或暂停时使旧编号失效。只有当前编号的完成回调可以设置 `idle` 或执行 `onDismiss`。

回弹可能同时驱动 dismissX、dismissY、inspectorProgress；等待该次动作所需的全部动画完成后才解锁。新触摸可以打断旧吸附并重新锁定，停止的动画不能随后恢复控件或关闭 viewer。

### 5.4 禁用原因区分

目前 `enabled=false` 会跳回合法目标，但 bool 无法区分退出、分享暂停和宽屏布局。建议替换为：

```ts
type MobileInteractionMode = "interactive" | "suspended" | "exiting";
```

Viewer 负责转换生命周期与布局：

| 条件                                         | mode        | 处理                                                         |
| -------------------------------------------- | ----------- | ------------------------------------------------------------ |
| 窄屏、phase=open、分享弹窗及其退出层均不存在 | interactive | 允许新的纵向操作                                             |
| 宽屏、进场、分享弹窗存在                     | suspended   | 取消手势与旧回调，停止动画，回到保留的抽屉目标；不接受新动作 |
| 窄屏正在退出                                 | exiting     | 停止新动作，保留已交接的关闭姿态，不把图片跳回原位           |

甩出结束时先形成快照，再交给 Viewer 记录 exitFrame 并关闭。进入 exiting 不清零 dismissX/Y，直到 viewer 卸载，避免共享元素接管前的跳动。手动关闭则冻结当时合法呈现，继续使用现有关闭方式。

宽屏只按桌面规则计算交互，不能让保留的移动端目标或阻塞状态继续限制宽屏切图。返回窄屏后按保留目标恢复抽屉。分享暂停也必须取消未完成的甩出回调，防止稍后自行关闭 viewer。

## 6. 各模块的职责与接线

### 6.1 移动端 hook

集中管理抽屉目标、纵向 activity、取消、动画编号和 stageBlocked 派生。连续的位移／透明度仍使用 MotionValue。仅在交互资格改变时通知 React。

不引入全局手势 store，不修改 `viewer-state.ts` 的 viewer 生命周期，也不把各个控件的可交互状态变成独立 state。

### 6.2 Viewer

组合现有生命周期／reveal、分享隔离和 hook 输出：

```ts
canNavigate =
  isInteractionEnabled &&
  !isShareDialogPresent &&
  (!isMobile || !mobile.isStageBlocked);

canUseChrome =
  isViewerControlsVisible &&
  isInteractionEnabled &&
  !isShareDialogPresent &&
  (!isMobile || !mobile.isStageBlocked);
```

缩略图沿用自己的 surface reveal 条件，但同样应用窄屏 stageBlocked。图片放大时保留缩略图选图能力；只通过原有 isZoomed 规则禁止触摸切图，不把 zoomed 等同于全部导航不可用。

`goToPhoto` 使用 canNavigate 作为统一入口保护，防止键盘、缩略图和其他命令绕过控件限制。Controller 仍保留自身 phase 和范围校验。

### 6.3 PhotoCarousel

将当前 `isSwipeDisabled` 替换为可选的同步阻塞信号：窄屏传入 stageBlocked，宽屏传 null。保留 `isInteractionEnabled` 和 `isZoomed` 两项条件。

- onSwiper 初始化时读取信号的 get()。
- 订阅 change，同步重新计算 `allowTouchMove`；信号、zoom 或 phase 改变时使用最新条件，不能把关闭抽屉直接等同于恢复触摸。
- 清理订阅，避免旧实例或跨断点后继续写值。
- 若禁用期间出现晚到的 `onSlideChange`，不更新业务选图；使用公开 `slideTo(activeIndex, 0)` 恢复受控索引，并防止回调递归。
- 保留 Virtual、A11y、simulateTouch、threshold 和 resize 策略。

### 6.4 控件与键盘

Toolbar 和 ThumbnailRail 新增显式的交互许可输入，与自身 reveal / phase 一起计算唯一 isInteractive；同一个结果用于 pointerEvents、inert、aria-hidden 和相关 disabled 属性。MotionValue opacity 继续只负责呈现。

不要给整个 media stage 设置 `pointer-events: none` 来阻止切图，否则会连同 pinch 和纵向手势一起禁用。隔离只作用于控件和 Swiper 的触摸切图许可。

键盘 hook 增加 `canNavigate`，左右键在阻塞时不执行选图；Escape 继续使用原有 enabled 条件与关闭动作。分享弹窗仍拥有自己的键盘与焦点处理。

### 6.5 信息抽屉与焦点

将移动端 `isInspectorInteractive` 传到信息面板，继续叠加 viewer interactive / visible。桌面按原规则处理。

沿用已有移动端把手作为关闭及键盘焦点入口。不新增标题或关闭按钮，不扩大工具栏尺寸，不改变现有面板 DOM 层级、布局、颜色或圆角。本轮未实现面板内容拖拽。

焦点规则：

- 键盘通过信息按钮打开时，按钮将变 inert，转移到已有抽屉把手；触摸拖动打开不强制抢焦点。
- 抽屉关闭或因 zoom 失去交互资格时，如果焦点在抽屉内，先移到现有 dialog 根节点；收起结束后可恢复到已可交互的信息按钮。
- 不对不在受影响区域的焦点执行无条件 focus。
- 分享隔离优先，退出分享期间不把焦点恢复到仍 inert 的舞台控件。
- viewer 最终关闭继续使用 `useDialogFocus` 恢复到照片触发器或 gallery。

## 8. 实施顺序

1. 在 hook 内明确活动状态、原生取消、多指忽略与动画完成归属，建立单一 stageBlocked 事实和离散渲染镜像。
2. 接入生命周期 mode，复核退出姿态与跨断点保留目标。
3. 接入 PhotoCarousel 同步订阅、晚到事件恢复；保留宽屏触摸规则。
4. 统一 Toolbar、ThumbnailRail、键盘和 goToPhoto 的交互资格。
5. 接入抽屉交互资格与现有把手的焦点恢复，不改变可见 UI。
6. 按验收矩阵检查，再更新文档实施记录；不在本轮顺带调整其他动画参数或图片资源策略。

预期涉及：`hooks/use-mobile-viewer-interactions.ts`、`viewer.tsx`、`photo-carousel.tsx`、`viewer-controls.tsx`、`viewer-info-panel.tsx`、`hooks/use-viewer-keyboard-navigation.ts`。数值规则确有必要提取时，复用现有 `lib/mobile-viewer-gesture.ts`，不新增通用协调包。

实施后执行相关文件格式检查、ESLint、TypeScript 和 `git diff --check`。它们只能证明静态一致性，不能代替真实触摸验收。

至少覆盖窄屏真实触摸设备、宽屏 iPad Safari、鼠标／键盘桌面浏览器。桌面模拟器能够补充布局与焦点检查，但不能把脚本构造 TouchEvent 或 props mock 当作真实 pinch / Swiper 竞争已通过的证据。

本方案不预设新增测试框架。若编写自动化验证，应检查事件序列导致的可观察行为或动画中断结果，避免只断言某个布尔公式／传给 mock 的 props。尚未执行的项目在实施记录中明确标为未验证。

## 10. 预期结果

用户仍通过原有方式切图、看信息和关闭照片；纵向操作期间不会通过残留控件或其他入口切走照片，抽屉收起完成才恢复舞台操作，取消和多指不会误触发退出。

实现仍由移动端 hook 隐藏过程复杂度，Viewer 组合产品规则，PhotoCarousel 适配 Swiper。优先提高现有交互的一致性，不改变图片渲染、资源预算和桌面导航方式。

### 11.4 设计复核与范围收缩

用户指出新增移动端关闭按钮突兀。复核确认初稿混入了可独立交付的 UI 改造，不能把它当成交互状态修复的必要条件。因此撤掉新增标题、关闭按钮及工具栏尺寸调整，最终面板 JSX 只增加既有 aside／把手的 ref，不增加节点。

核心保留理由：

- 四种 activity 对应实际存在的空闲、跟手、回弹、甩出，避免提前解锁；它是 hook 内部过程标记，不是新增通用状态机。
- 同步阻塞信号用于 Swiper 事件期间更新许可，React 镜像用于 inert／disabled；两者表达同一个事实，不分别修改。
- 动画编号及完成屏障用于中断旧动作，取消／多指忽略用于避免异常释放被解释为关闭。
- 焦点处理使用现有元素，是引入 inert 后的配套，避免键盘停在被禁用的工具栏。

进一步移除冗余的 inspectorProgress 逐帧监听和 GestureMemo 引用；阻塞只在手势、目标、模式、多指或动画完成事件中更新。模式同步增加变化判断，onDismiss 函数引用变化只更新最新回调，不反复执行暂停／取消流程。

工具栏也移除本轮新增的 disabled：父层 inert、aria-hidden 及 pointer-events 已能隔离操作，而现有 circle-button 的 disabled 样式会额外改变透明度。保留原有视觉动画，不叠加这层样式效果。

收缩后补验：浏览器确认不存在新增 h2／关闭按钮，键盘焦点进入原有把手；方向键不切图，回车关闭后先停在 dialog，收起完成恢复信息按钮。纵向锁、多指加入后剩余单指、touchcancel、回弹解锁及新的上滑再次通过 Chrome 原生触摸模拟。ESLint、TypeScript 和 diff 检查通过。

这次优化增加了局部生命周期逻辑与维护成本，并非零成本或唯一可行实现。当前收益是交互正确性和操作一致性；未测量 FPS 或 CPU 收益，不把它称作已证实的性能提升。

## 12. 再次评估：当前实现的复杂度不成比例

本节取代第 11.4 节对“当前结构值得整体保留”的判断。撤掉额外 UI 只能解决范围扩张，不能证明剩余设计足够简单。本轮重新对照 HEAD 原实现、当前六个文件、Afilmory、本地 Swiper／use-gesture／Motion 源码，不修改产品代码。

### 12.1 目标成立，但验证并未证明这套实现必要

可以直接从原源码确认：工具栏／缩略图的可交互条件未随抽屉视觉隐藏更新；infoOpen 表达目标而不是收起过程；原生 cancel 未区别于正常释放。这些是值得修复的具体缺口。

不能由此推出：React 更新一定来不及限制 Swiper、每个晚到的 slideChange 都要主动回滚、所有控件都要等三个动画完成、完整焦点返回流程是本轮的必需功能。

此前触摸模拟验证说明“新实现处理了所测序列”，没有用较小方案做对照，也没有复现原实现的同步竞争。Afilmory 使用 React 的纵向活动／抽屉可见布尔量和 effect 更新 allowTouchMove，也不提供当前这套同步阻塞通道。这个事实不证明简单实现绝无竞态，但意味着引入更重机制的举证不足。

当前六个代码文件净增 275 行；移动端 hook 从 322 行增加至 488 行，Viewer 从 356 行增加至 435 行。行数本身不是过度设计的判据，真正的成本是下列跨模块协议和手动维护的关系。

### 12.3 当前还扩大了产品行为

canUseChrome 直接继承 canNavigate，因此一次很小的下拉或图片回弹就会使关闭／分享按钮一起不可操作。原有 dismiss opacity 在短距离下拉时仍接近 1，用户能看到按钮。禁止切图并不自动意味着必须禁止关闭。

这是新增的产品规则，不是单纯修复透明控件。重新实施时应先保持已有关闭和分享语义；导航占用限制导航，工具栏隔离按实际面板呈现／生命周期决定。不要为了“所有控件统一一个条件”而改变无关动作。

多指与原生取消仍值得保留，但应放在本地手势的 ignore／cancel 流程中，避免把它扩成统管所有输入的全局优先级系统。舞台捕获入口有范围假设，不能因为状态字段齐全就认定所有跨区域接触都已覆盖。本轮另外用 Chrome 原生触摸模拟检查了“先缩略图、再舞台，两指依次释放”，该序列没有残留 inert；不把未复现的事件范围推断记成现存故障。

### 12.4 更小的替代方案

1. 保留原有 infoOpen、三个位移／进度 MotionValue、closingRef 和已有阈值／视觉函数。
2. 增加一个 gestureBusy，纵向开始设 true，回弹全部完成才清 false；释放、取消和中断走同一局部清理路径。由 infoOpen || gestureBusy 派生窄屏切图限制。若工具栏需要单独跟随抽屉实际呈现，再从现有 inspectorProgress 的阈值派生一个离散 inspectorPresent，只在跨阈值时更新 React；不要把所有许可重新聚合成发布快照。
3. PhotoCarousel 用普通 bool 控制 allowTouchMove，保持原有受控索引同步；不订阅额外 MotionValue，不在 slideChange 中加入自动回滚。
4. 导航入口、缩略图和左右键使用派生限制；抽屉隐藏的工具栏沿用现有 inert／aria-hidden／pointer-events，并采用 infoOpen／inspectorPresent 条件。保留 Escape 语义，不强行让关闭／分享等同于导航。这里的额外可见性事实有明确消费者，不把“只加一个 bool”当成解决所有交互的承诺。
5. 保留必要的原生 cancel、多指忽略与退出冻结；动画中断用一个本地编号或现有 controls 管理，不引入发布器和手填完成计数。
6. 焦点处理复用现有 dialog trap 和现有 DOM，去掉自动返回意图状态。布局、尺寸、透明度、动画参数、img 和图片加载均保持。

这个方案仍有手势和动画生命周期成本，不承诺“十几行就能解决全部情况”。其简化标准是减少状态表示、调用方需要知道的协议，以及未经复现的自动修复机制；不能靠删掉必要的取消／回弹处理来追求行数。

### 12.5 实施前后的证明要求

较小实现优先验证抽屉收起末段、下拉回弹、近 45° 斜滑、多指接续、原生取消、宽窄断点、分享退出、键盘焦点和关闭姿态。对争议点保留操作序列与索引／URL 证据。

若 bool 方案出现首次事件漂移，先复现、定位 listener 时序，再只修 PhotoCarousel 的事件适配；如果无法复现，不预置“同步通道 + 回滚”组合。动画停止的 finished 行为需要按本地 Motion 实现检查，并验证取消编号能排除旧完成；不能仅用静态类型判断安全。

当前结论：优化目标值得继续，但当前实现不应因检查通过就直接视为最终方案。建议收缩重写以上实现，而非继续在现有协调逻辑上叠加补丁。本次仅更新评估，代码仍是待收缩版本。

### 13.2 新确认的性能风险：输入许可扰动资源生命周期

`Viewer` 现在把移动端 `isInspectorInteractive` 传给 `ViewerInfoPanel.isViewerInteractive`。hook 在抽屉已打开、开始纵向拖动或加入第二指时把它设为 false；回弹或恢复操作后又设为 true。

面板原有的 `isInteractive` 同时用于 `inert` 和 `ViewerInfoPanelContent.isActive`。后者继续传给 `PhotoHistogram` 与 `ViewerLocationMap`。因此这次修改虽然没有直接改地图／直方图文件，却把原本的输入保护传播到了资源 effect：

- 地图的 ResizeObserver 随 isActive 清理、重新建立；恢复活动时，另一个 effect 再调用 `map.resize()` 和 `map.jumpTo()`，即使照片与坐标都没变化。
- 直方图的 ResizeObserver 同样清理、重建；获取缓存数据及绘制 effect 重新执行，正在进行的直方图动画被取消，内部视觉记录改为目标数据。
- 地图实例仍然保留，没有重新创建。直方图有结果缓存及请求复用，不应把这些额外调用描述为必然重新下载／计算，也不应声称每次重播完整动画。

这是源码可确认的额外生命周期工作，发生在交互开始或恢复的边界。没有帧时间对照，不能据此宣称已经掉帧或视觉跳变；但它不是纵向手势修复所必需的工作，应优先消除这条耦合。修复可以局限在面板的输入许可和内容活动条件，不需要顺带改地图实现、直方图缓存或建立资源调度器。

### 13.3 性能与 UI 的判断边界

当前 publishInteraction 先比较离散快照，连续位置由 MotionValue 更新，没有在动画每帧调用 React setState。增加 ref 或布尔 MotionValue 不等于降低帧率；当前批评重点是跨组件一致性协议与不必要的消费者副作用。

流畅性也包括立即响应。可见关闭按钮在小幅拖动后被设为 inert，即使动画仍以稳定帧率运行，也会让这段操作不可响应。回弹占用应只持续到相关动作真正需要的终点，不因为统一许可而额外阻塞无关控件。

对比 HEAD 与当前 JSX，新增移动端标题、关闭按钮及工具栏尺寸修改已撤回，当前没有新增 DOM 节点。但交互资格仍发生变化，且上述内容活动切换有潜在视觉影响，不能把“DOM 没增加”当作 UI 行为完全不受影响的证明。

### 13.4 最小收缩顺序

1. 先拆开面板临时输入保护与内容资源活动，取消导航限制对关闭／分享的无依据传播。
2. 保留方向锁、取消／多指保护和一次接管停止动画；局部中断保护及退出冻结继续保留。
3. 撤掉未有复现依据的 slideChange 回滚；把阻塞输入收回普通布尔条件，同时验证抽屉收起末段、纵向回弹和斜滑竞争。若出现竞态，记录事件序列并只修必要的适配位置。
4. 收缩焦点意图和快照发布协议；不更改动画参数、手势阈值、图片加载、缩放、Swiper 配置及布局。

既往浏览器验证只证明当前实现能处理已测序列，没有证明它优于更小实现，也没有原版与当前版本的帧时间对照。后续若实施收缩，需要回归上述行为；只有涉及新的性能取舍时再做针对性的主线程／帧时间对照，不新增长期运行的监控机制或测试框架。

## 15. 移动端面板呈现时禁止图片缩放（2026-10-01）

### 15.1 产品规则与实现边界

### 16.1 P1：导航锁拒绝轮播已完成的切图通知

位置：`viewer.tsx` 的 `goToPhoto` 和传给 `PhotoCarousel.onActiveIndexChange` 的回调。

4. 再抬第二指，导航恢复，但状态错位仍存在。下一张只有缩略图，原图／缩放组件仍按上一张的 React activeIndex 挂载。点击已被 React 标为当前的 `DSC08230` 缩略图也不会恢复，因为 activeIndex 没有变化，轮播同步 effect 不会重跑。
