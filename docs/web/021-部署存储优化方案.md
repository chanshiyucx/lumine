# 部署存储优化方案

## 文档状态

- 状态：待评审
- 日期：2026-09-21
- 范围：`web/` 的 Next.js 页面生成策略
- 首要约束：不得改变现有页面展示效果、交互方式、URL 语义和内容更新时效

## 背景

Vercel 的 `Deployment Storage` 已达到 `18.86 GB / 10 GB`。该指标统计被保留部署的构建输出和静态资源，不是访问流量，也不是 Build Cache、CDN Cache 或照片源文件占用。

当前代码仓库本身很小，媒体文件由 `MEDIA_ORIGIN` 指向的独立静态存储提供。部署体积主要来自 Next.js 在构建阶段生成的照片详情页，而不是 Git 中的大文件。

Vercel 对 Deployment Storage 的定义和优化建议见：

- [Deployment Storage](https://vercel.com/docs/deployment-storage)
- [Optimize Deployment Storage](https://vercel.com/docs/deployment-storage/optimize)
- [Deployment Retention](https://vercel.com/docs/deployment-retention)

## 现状证据

当前 `manifest.json` 包含 448 张照片。`/photos/[photoId]` 路由在构建时为每张照片生成一个静态页面，同时每个页面都向客户端传递完整的照片集合。

关键实现：

1. `web/app/photos/[photoId]/page.tsx` 中的 `generateStaticParams()` 返回全部照片 slug。
2. 同一路由中的 `getRequestedPhoto()` 返回当前照片和完整 `photoCollection.photos`。
3. `PhotoPage` 把完整数组传给 Client Component `PhotoGallery`。
4. React Server Component 到 Client Component 的接口会序列化完整数组，并将它写入 HTML 和 RSC 产物。

当前生产构建结果：

| 产物 | 数量 | 实际字节总量 |
| --- | ---: | ---: |
| 照片详情 HTML | 448 | 238.9 MiB |
| 照片详情 RSC | 1,792 | 573.0 MiB |
| 其他照片路由文件 | 若干 | 约 0.4 MiB |
| `/photos` 路由合计 | — | 812.3 MiB |

抽查任意一个照片 HTML，都能找到 448 组 `slug`、`thumbnail` 和 `original` 字段。这说明每个详情页都重复保存了整个照片目录。

当前增长模型近似为：

```text
构建输出大小 ≈ 照片数量 × 每个页面携带的完整照片目录
```

因此照片详情页的构建输出呈近似 O(N²) 增长。照片数量翻倍时，这部分部署产物可能接近四倍，而不是两倍。

## 目标

### 必须达成

1. 不改变首页、相册页、地图页和照片查看器的视觉结果。
2. 不改变点击照片、共享元素动画、上一张/下一张、缩略图轨道、键盘、触摸手势和缩放交互。
3. 不改变 URL：照片仍使用 `/photos/:photoId`。
4. 不改变浏览器前进、后退、关闭查看器、滚动位置恢复和焦点恢复行为。
5. 不改变直接打开照片链接、刷新详情页、分享、Metadata 和 Open Graph 图片行为。
6. 不改变当前 30 秒照片清单更新时效。
7. 新部署不再携带全部 448 个照片详情页的静态副本。
8. 建立可自动验证的构建产物预算，避免问题回归。

### 非目标

本方案第一阶段不处理以下事项：

1. 不重新设计 Gallery 或 Viewer。
2. 不改变照片清单的数据格式。
3. 不把完整照片清单改成客户端二次请求。
4. 不懒加载 EXIF 或当前查看器依赖的数据。
5. 不迁移媒体存储。
6. 不通过清理 Build Cache、CDN Cache 或 Data Cache 解决 Deployment Storage。
7. 不保证已经产生的 `18.86 GB` 在部署新版本后立即从当前计费周期中消失。

## 行为兼容契约

实现前后必须保持以下外部可观察行为一致。

### 首页与相册

- 首页继续展示完整照片瀑布流。
- 相册页继续只展示当前相册中的照片。
- 图片尺寸、顺序、缩略图、ThumbHash、悬停信息和虚拟滚动不变。
- 点击照片时仍从对应瀑布流卡片执行共享元素过渡。

### Viewer

- 当前照片索引和照片顺序不变。
- 上一张、下一张、键盘方向键、触摸滑动和缩略图选择不变。
- 信息面板、直方图、原图渐进加载、下载和分享数据不变。
- 双击缩放、滚轮、双指缩放和移动端关闭手势不变。

### URL 与历史记录

- 从首页或相册打开照片后，地址更新为 `/photos/:photoId`。
- Viewer 内切换照片继续使用替换历史记录的语义。
- 关闭 Viewer 后恢复打开前的首页或相册 URL。
- 浏览器前进和后退继续同步 Viewer 状态。
- 直接打开 `/photos/:photoId` 时 Viewer 立即处于打开状态。

### 分享与 SEO

- 分享链接格式不变。
- 页面标题、Open Graph 和 Twitter Metadata 不变。
- `/photos/:photoId/opengraph-image` 的图片内容和尺寸不变。
- 不存在的 `photoId` 继续返回 404。

## 现有交互为何可以保持不变

站内打开 Viewer 时不会发起到 `/photos/:photoId` 的 Next.js 页面导航。

`useViewerController` 当前通过浏览器 History API 管理 URL：

```text
点击照片        -> history.pushState
Viewer 内切换   -> history.replaceState
关闭 Viewer     -> history.back 或 history.replaceState
前进/后退       -> popstate 同步 Viewer 状态
```

照片卡片本身是 `<button>`，不是会触发服务端页面请求的 `<a>`。因此改变 `/photos/[photoId]` 的服务端生成时机，不会进入正常的站内 Viewer 交互路径。

只有以下情况会真正请求详情页：

1. 用户直接打开分享链接。
2. 用户在 `/photos/:photoId` 刷新浏览器。
3. 外部爬虫或预览服务请求分享链接。

## 设计决策

### 决策：详情页改为按需 ISR

保留现有页面模块、Client Component 接口和 Viewer 状态实现，只改变 `/photos/[photoId]` 的参数生成策略。

当前实现：

```ts
export async function generateStaticParams() {
  const photoCollection = await getPhotoCollection()

  return photoCollection.photos.map((photo) => ({
    photoId: photo.slug,
  }))
}
```

目标实现：

```ts
export async function generateStaticParams() {
  return []
}
```

当前项目未启用 Next.js Cache Components。按照当前 Next.js 版本的规则，`generateStaticParams()` 返回空数组表示：

1. 构建阶段不生成任何具体照片详情页。
2. 未知参数仍然允许访问，因为 `dynamicParams` 默认为 `true`。
3. 某个照片详情页第一次被直接请求时，由服务端生成。
4. 生成结果按照现有数据缓存规则进入 ISR 缓存。
5. 后续请求复用缓存结果，并继续遵守现有 30 秒 revalidate 设置。

### seam 选择

本次变更的 seam 放在路由的“参数生成策略”上，而不是 Gallery/Viewer 的数据接口上。

这样做的原因：

- 路由生成策略决定页面是在构建期还是请求期生成，是部署体积问题的直接来源。
- `PhotoGallery` 的 `photos` 接口承载现有全部交互能力，第一阶段修改它会扩大回归范围。
- URL 与 History API 行为完全位于客户端，和静态参数枚举没有耦合。
- 变更集中在一个文件和一个函数，具有最高 locality。

第一阶段不新增数据获取 Adapter 或额外 Route Handler。当前只有一种媒体清单来源，新增抽象不会形成真实 seam，只会增加维护成本。

## 请求与存储流程

### 修改前

```text
部署开始
  -> 下载 manifest.json
  -> 枚举 448 个 photoId
  -> 生成 448 个完整页面
  -> 每个页面序列化 448 张照片
  -> 上传约 812 MiB 的照片详情 HTML/RSC
  -> 每个被保留部署保存一份
```

### 修改后

```text
部署开始
  -> 不枚举具体 photoId
  -> 上传动态路由实现
  -> 不上传 448 个详情页副本

站内查看照片
  -> 使用已有 PhotoGallery 数据
  -> History API 更新 URL
  -> 不请求详情页

直接访问分享链接
  -> 读取 manifest.json
  -> 校验 photoId
  -> 生成与当前完全相同的页面
  -> 写入该路径的 ISR 缓存
```

## 缓存策略

### 第一阶段保持 30 秒不变

`getPhotoCollection()` 当前使用：

```ts
next: { revalidate: 30 }
```

虽然 30 秒比较激进，但它属于现有内容更新契约。第一阶段不修改该值，避免用户上传照片后刷新网站却看不到变化。

需要明确区分：

- 构建时生成的 448 个页面属于 Deployment Storage 的主要膨胀来源。
- 请求后产生的页面属于 ISR 生命周期和运行时缓存问题。
- Build Cache、CDN Cache 和 Data Cache 不是本次 18.86 GB Deployment Storage 的直接修复对象。

### 第二阶段候选：发布后按需失效

未来可以在媒体文件和 `manifest.json` 发布完成后调用受保护的 revalidation Route Handler，用 tag 或 path 主动失效缓存，再把固定 30 秒轮询调整为更长周期。

该方案需要同时设计：

1. 发布脚本如何调用 Web 项目。
2. 鉴权密钥如何管理。
3. manifest 上传和缓存失效的顺序。
4. 失败重试和幂等性。
5. 首页、相册、地图、照片页和 OG 路径的失效范围。

这属于独立改造，不纳入第一阶段，避免把线上存储修复和发布流程变更绑定在一起。

## 性能影响

### 站内操作

没有预期性能变化。站内 Viewer 不请求照片详情页，现有照片数组、虚拟滚动和图片加载逻辑全部保持不变。

### 直接访问分享链接

某个路径第一次被直接访问时会发生一次服务端生成，首字节时间可能比预生成页面更长。之后由 ISR 缓存复用。

风险缓解：

1. manifest 和照片资源继续由现有缓存提供。
2. 页面结构与序列化工作量不变，只有执行时机改变。
3. 照片卡片不是链接，普通爬虫不会从首页自动枚举全部照片详情路径。
4. 如线上观测发现冷启动不可接受，可只预生成少量最常访问或最近照片，而不是恢复全量生成。

### 构建与部署

预计变化：

- 构建阶段减少 448 次照片详情页渲染。
- `/photos` 构建输出从约 812.3 MiB 降至路由实现和少量公共产物。
- 构建时间下降。
- 新部署的 Deployment Storage 显著下降。
- Vercel 的 Functions Storage 可能存在小幅变化，应单独观察，不能与 Deployment Storage 混为一项。

## 回滚方案

### 应用回滚

如果出现直接链接、Metadata、OG、404 或 Viewer 行为异常：

1. 立即把域名回滚到修改前记录的 Production 部署。
2. 不在故障部署上继续叠加修复。
3. 在 Preview 中复现并修正。

### 代码回滚

恢复原来的全量 `generateStaticParams()` 可以恢复构建期预生成行为，但也会恢复部署体积问题。只有确认故障和按需生成直接相关时才执行。

## 风险与应对

### 风险一：直接链接首次访问变慢

原因：页面从构建期生成改为请求期首次生成。

应对：

- 记录冷访问和缓存访问 TTFB。
- 仅在数据证明有必要时预生成少量热门页面。
- 不直接退回全量 448 个页面。

### 风险二：外部爬虫请求大量照片路径

当前照片卡片不输出详情页链接，普通爬虫无法从 Gallery 自动枚举所有路径。分享平台只请求实际分享的链接和 OG 图片，因此风险较低。

如未来为 SEO 把照片卡片改成链接，需要重新评估爬虫是否会生成全部 ISR 页面，并增加机器人策略或预生成上限。

### 风险三：开启 Cache Components 后构建失败

当前 Next.js 版本在启用 Cache Components 时不允许 `generateStaticParams()` 返回空数组。项目当前未启用该功能。

后续如启用 `cacheComponents`，必须同时重新评估动态参数策略，不能直接沿用本方案而忽略构建检查。

### 风险四：误把历史用量当成方案无效

Vercel Deployment Storage 按计费周期记录。新版本变小不会让历史 `18.86 GB` 立即归零。

方案是否生效应通过以下信号判断：

1. 新构建中照片详情预渲染数量为 0。
2. Preview 的 Static Assets 明显下降。
3. 新部署后项目存储增长斜率显著下降。
4. 下一个计费周期不再快速触顶。

## 被否决的替代方案

### 方案 A：继续全量预生成，只缩短部署保留时间

否决原因：只缓解部署数量，没有解决单个部署随照片数量平方增长的问题。频繁部署后仍会再次超过配额。

### 方案 B：把照片清单改为客户端请求

否决原因：虽然可以进一步减少 HTML/RSC，但会引入第二次网络请求、加载状态、错误状态和 hydration 时序变化，无法满足第一阶段“展示和交互完全不变”的约束。

### 方案 C：只向详情页传当前照片

否决原因：现有 Viewer 需要完整序列来支持上一张/下一张、缩略图轨道、键盘、手势、信息面板和关闭后的 Gallery。直接缩减 props 会改变交互模型。

### 方案 D：强制所有详情页动态渲染且不缓存

否决原因：会让每次直接访问都承担远程 manifest 请求、校验、渲染和序列化成本，增加计算用量和延迟。按需 ISR 更符合当前内容模型。

### 方案 E：配置 `outputFileTracingExcludes`

否决原因：812.3 MiB 是真实生成的 HTML/RSC 页面，不是文件追踪误包含的依赖。排除追踪文件不能删除实际页面输出，并可能造成运行时缺文件。

### 方案 F：清理 Vercel Cache

否决原因：Build Cache、CDN Cache 和 Data Cache 与 Deployment Storage 是不同资源。清理缓存不能从根本上缩小新部署产物，还可能导致额外再生成。

### 方案 G：直接升级 Vercel 套餐

否决原因：升级只能提高额度或转为付费存储，无法解决 O(N²) 的构建模型。代码修复仍然必要。

## 成功标准

本方案完成的判定标准：

1. 页面和交互回归矩阵全部通过。
2. `/photos/:photoId`、Metadata、OG 和 404 行为保持一致。
3. 构建期照片详情路径从 448 降至 0。
4. `/photos` 构建输出从约 812.3 MiB 降至预算以内。
5. 新 Preview 的 Deployment Storage 产物显著小于基线。
6. 连续多次部署不会再按约 0.8 GiB/次累积照片详情静态产物。
7. 构建产物预算进入日常验证流程，未来新增照片时不会静默恢复 O(N²) 输出。

## 后续候选工作

第一阶段稳定后，可以独立评估：

1. manifest 发布完成后的按需缓存失效。
2. 以最近照片或真实访问数据选择少量预生成路径。
3. 为直接分享链接增加冷启动监控。
4. 在不改变首屏体验的前提下，研究版本化公共照片目录，进一步减少单次页面响应体积。
5. 增加端到端测试覆盖 Viewer URL、History API 和分享入口。

这些工作不应阻塞本次 Deployment Storage 修复，也不应和第一阶段一次性上线。
