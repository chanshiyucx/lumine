# 可读名称路由方案

日期：2026-09-28
状态：代码已实施；生产构建受媒体数据版本阻塞

## 决策

公开地址继续使用相册文件夹名与照片标题生成的 slug：`/albums/{albumId}`、`/photos/{photoId}`。路由参数统一命名为 `albumId`、`photoId`；其中 `albumId` 的值是相册文件夹名，`photoId` 的值是照片 slug，不是哈希。例如相册 Königssee 的路径为 `/albums/20260524-K%C3%B6nigssee`。`/albums`、`/map` 等固定页面保持原样；分享链接、Viewer 历史地址、地图链接和 Open Graph 图片地址复用 `route-paths.ts` 的路径函数。

路径函数对单个动态段执行 NFC 归一化和 `encodeURIComponent()`。相册文件夹键、照片 slug 在资源集合中保持 NFC 形式；标题中的空白和 `/` 沿用已有的照片 slug 规则。浏览器地址中的百分号编码只是 URL 表示方式，不替换公开资源名称，也不引入哈希 ID。pipeline 与 manifest 契约不变。

## 路由参数查找

本项目的 Next.js 16.3.4 对同一路径在不同入口传递的参数形式不同：页面组件收到仍带 URI 编码的段，例如 `20260524-K%C3%B6nigssee`；`generateMetadata` 与文件式 Open Graph 图片收到已解码的 `20260524-Königssee`。页面入口用 `decodeEncodedPathSegment()` 解码一次，其他两个入口直接使用参数。这个差异与 [Next.js 对路由匹配值的解码](https://github.com/vercel/next.js/blob/v16.3.4/packages/next/src/shared/lib/router/utils/route-matcher.ts)及[页面动态段的再次编码](https://github.com/vercel/next.js/blob/v16.3.4/packages/next/src/shared/lib/router/utils/get-dynamic-param.ts)一致。

各入口将规范的相簿名或照片 slug 传给共用 `_data.ts` 加载器。相簿通过 `catalog.getByKey(albumId)` 做 NFC 归一化并查找一次，照片将 `photoId` 归一化后按 slug 查找一次；未找到才返回 404。资源查找不根据命中情况猜测参数是否需要解码。

Viewer 从浏览器的原始 `pathname` 读取照片段，沿用 `getPhotoSlugFromPathname()` 的单次解码；它不处理 Next.js 的 `params`。相册页 `generateStaticParams()` 返回未做 URI 编码的相册文件夹键，照片页保持按需生成。

## 此次全部相簿详情页 404 的原因

开发服务器运行期间曾将动态目录从哈希实现的 `app/albums/[albumId]` 改为 `app/albums/[albumKey]`。当时源码只剩 `[albumKey]`，但 `.next/dev/server/app-paths-manifest.json` 同时登记了两个匹配 `/albums/:segment` 的路由，普通名称 `20260307-Mittenwald` 也返回 404；这与 URL 中是否有特殊字符无关。现在目录名统一为 `[albumId]`，其值仍是可读相簿名。

重启开发服务器后，路由清单只保留当前目录对应的路由，`/albums/20260307-Mittenwald` 和 `/albums/20260524-K%C3%B6nigssee` 均返回 200。遇到动态目录重命名后的同类现象，应先重启开发服务器并检查生成的路由清单，而不是在资源查找层增加兜底。生产部署由构建重新生成路由清单。

## 范围与限制

照片 slug 仍由标题生成；若不同照片生成相同 slug，现有单段路径无法区分。本项目的照片名称唯一，本次不引入序号、哈希或别名机制。相册文件夹或照片标题改名时，其公开地址随之变化；此次不维护旧地址。

类型检查与 lint 已通过。当前 `MEDIA_ORIGIN` 提供的 manifest 版本仍早于 Web 既有的 v3 schema，因此生产构建尚不能完成页面数据收集；需提供 v3 媒体数据后再运行生产构建。本次不新增或运行测试。
