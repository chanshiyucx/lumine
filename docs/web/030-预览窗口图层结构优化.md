# Viewer 图层结构与标签页恢复优化

- 状态：历史实验；Portal 挂载已撤回，且手动验证对标签页恢复闪烁无改善
- 日期：2026-09-24
- 范围：Viewer 的挂载位置、全屏背景与内容层的进退场结构

> 后续复核发现 Portal 改造会使照片直链失去原有的服务端预览 DOM，因此已撤回。以下保留当时的实验记录，不代表当前实现。

## 背景与判断

在 macOS Chrome 中，即使暂时让 `ProgressivePhoto` 只显示缩略图，已打开的 Viewer 从其他标签页恢复时仍可能短暂闪烁。这说明大尺寸 AVIF 原图不是此轮现象的必要条件，但仅凭现象和组件树，尚不能确定是某个浏览器合成层、图片解码还是页面重绘造成了那一帧。

当前 Viewer 挂在 `PageScrollArea` 的滚动视口下；带全屏透明度动画的外层 `m.div` 同时包裹背景、轮播、工具栏、缩略图、信息面板及共享图片过渡。Afilmory 将 Viewer 放在 `body` Portal 中，并把背景与内容放在并列层。两者的结构差异值得采用，但不能直接推断 Portal 会获得特定的 GPU 合成层，也不能保证完全消除 Chrome 的恢复闪烁。

## 目标

1. Viewer 脱离画廊滚动区域的 DOM 祖先和层叠上下文，仍保持在原有 React 树中。
2. Viewer 打开期间，桌面端有不参与整窗透明度进退场动画的不透明纯色底层；背景动画和交互内容分别绘制。
3. 保持已有淡入淡出、共享图片转场、移动端下拉关闭、滚动锁定、焦点恢复及键盘操作的语义。
4. 不修改当前缩略图或原图的加载、解码、缓存及 Swiper 更新策略，以便手动观察此轮结构调整的效果。

## 实施方案

### 1. 在画廊入口创建 Portal

`PhotoGallery` 通过 `useSyncExternalStore` 在服务端和 hydration 时返回空挂载目标，客户端恢复后取得稳定的 `document.body`，再用 `createPortal` 渲染已经存在的 `Viewer`。Viewer 的状态和事件仍来自 `useViewerController`，因此切图、路由同步以及关闭回调不移动。首次直达照片页面时，服务端与客户端首次渲染都不访问 `document`，避免 hydration 结果不一致。

React Portal 会保留 React 上下文和事件传播关系。DOM 位置变化后，`RemoveScroll` 位于 `body` 下方；画廊和 Header 的 `inert` 控制维持原样。共享图片转场使用的源图片与目标舞台继续用视口坐标计算，不依赖共同的 DOM 父节点。

### 2. 拆开 Viewer 的动画外壳

最外层保留一个不带透明度动画的固定定位对话框节点，承载 `role="dialog"`、焦点引用和统一的层叠上下文。其内部为三个并列层：

1. **静态纯色底层**：仅在桌面端 `phase === 'open'` 时可见，覆盖整个视口，不做淡入淡出。它位于其他 Viewer 层之下，防止正常打开状态下动画背景暂时未呈现时露出底页。
2. **现有动画背景层**：保留 `ViewerBackdrop`、ThumbHash、照片切换渐变及原有的入场、退场时序。共享图片入场时仍允许底页参与转场。
3. **前景内容层**：包含轮播、工具栏、缩略图、信息面板、分享对话框和共享图片转场。原本加在整个 Viewer 外壳上的淡入淡出改由该层负责，其完成回调继续推进 Viewer 状态机。

从 `open` 切到 `exiting` 时，静态底层立即隐藏；动画背景从完整不透明状态开始退场。普通淡出时背景与前景使用相同的退场时长，避免前景完成回调卸载 Viewer 时背景还在绘制；共享图片退场沿用背景原有的较长时长。这样不会让静态底层阻断关闭时应露出的画廊。

移动端现有下拉关闭手势会降低背景透明度以露出底页，因此不启用静态纯色底层，避免手势时出现额外的不透明覆盖。移动端同样受益于 Portal 以及背景、内容层分离。

## 明确不采纳的推断

- `decoding="async"` 是图片解码提示，不足以证明每次切回标签页都会空白一帧；本轮不切换为原生 `<img>` 或强制 `decoding="sync"`。
- `ResizeObserver` 并非每次标签页恢复都会调用 `swiper.update()`；本轮不关闭已有的尺寸修正逻辑。
- 相同的 `z-index` 数值不等于随机的图层“争抢”。Portal 和独立背景是更清晰的层叠设计，不承诺浏览器一定分配独立 GPU 纹理或彻底消除闪烁。
- Afilmory 的图片局部 ThumbHash 补位主要服务于入场衔接，并非常驻的标签页恢复兜底；本轮不额外复制该条件层。

## 手动观察要点

按当前缩略图模式，重点观察多窗口反复切走再返回时，是否仍有底页或 Viewer 整体短暂透出。随后分别检查照片页直达、画廊点击入场、淡入淡出关闭、共享图片转场、切图、工具栏与分享框焦点、桌面滚动锁定，以及移动端下拉关闭是否保持原有效果。若仍有闪烁，应区分整窗透出与仅照片区域重绘，再决定下一轮修改位置。

## 手动验证结果与下一步

在仅显示缩略图的调试状态下，Portal 与图层拆分没有改善标签页恢复时的短暂闪烁。用户将 `PhotoMasonry` 和 `ViewerThumbnailRail` 同时注释后，闪烁消失。这把关注点转向两处区域的总绘制负担及其虚拟滚动活动，但注释整个组件也同时移除了缩略图、ThumbHash、滚动容器和动画，因此不能单独归因于 `@tanstack/react-virtual`。

代码中有两个可核查的差异：背景 `PhotoMasonry` 在 Viewer 打开后仍保持虚拟器观察，虽然画廊根节点已设为 `inert`；`ThumbnailRail` 使用 TanStack React 适配器默认的 `useFlushSync: true`，而 `PhotoMasonry` 已显式关闭它。下一轮若要隔离虚拟器，应保持两处区域及其图片继续渲染，只暂停或调整虚拟器的观察和同步提交，再由同一手动场景比较；仅删除组件无法区分 JavaScript 调度与图片/图层开销。
