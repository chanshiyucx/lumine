## 1. 目标与边界

### 1.1 必须达成

1. 用 Finder 标签标记私密照片，和公开照片走同一条构建流程。
2. 未解锁时，首页、相簿页、地图页的呈现和现在完全一样，不含任何私密照片。
3. 输入固定密码解锁后，私密照片出现在首页、相簿页和地图页。私密照片和公开照片**属于同一个相簿**，在地图上也是同一个点，不拆成两部分。
4. 解锁状态保持 3 天，期间不需要重新输入。
5. 未解锁前，任何途径都拿不到私密照片：直接打开 `/photos/DSC09211` 这类页面链接，按命名规律猜媒体路径，读取公开的 manifest，读取 CDN 缓存，都不行。
6. 公开站点的速度、缓存和费用不受影响。

### 1.2 不防范的情况

- 已解锁设备上的人把图片存下来再转发。任何方案都防不住。
- 有效的签名图片链接在过期前（最多 3 天）被转发出去。
- 一张照片曾经公开过，之后再改成私密：在改动之前，它已经可能被别人看过、缓存过。

## 2. 总体架构

隔离分三层：数据、页面、媒体。

```text
              公开访客                            已解锁（带 cookie）
                 │                                      │
     proxy.ts 不运行（matcher 要求有 cookie）   proxy.ts 校验 cookie，rewrite /x → /vault/x
                 │                                      │
   静态/ISR 页面（和现在完全一样）            动态页面（force-dynamic，不进任何缓存）
   数据：public/manifest.json                 数据：公开与私密 manifest 在服务端合并
   图片：cloud.shiyu.me/public/…              私密图片：private.shiyu.me/…?exp=…&sig=…
         （R2 自定义域名，WAF 只放行 /public/）       （Worker：校验签名后读取 R2 的 private/）
```

| 层 | 未解锁 | 解锁后 | 防住的泄漏途径 |
| --- | --- | --- | --- |
| 数据 | 公开 manifest 中没有私密照片 | 私密 manifest 只有服务端能读 | 读取公开 manifest |
| 页面 | 静态页面，私密 slug 返回的 404 和“照片不存在”完全一样 | 动态渲染，不缓存 | 猜页面链接、静态产物和 CDN 缓存泄漏 |
| 媒体 | `/public/` 以外的路径一律被 WAF 拦截 | 带签名、有过期时间的 URL，由 Worker 校验 | 猜媒体路径、直接访问桶 |

## 3. 关键决策

### 3.1 存储：单桶 + 目录分离 + WAF 白名单

所有照片放在同一个 R2 桶 `gallery` 里，公开和私密照片分别放在 `public/` 和 `private/` 下。公开域名 `cloud.shiyu.me` 上配一条 WAF 规则，只放行 `/public/` 开头的路径。私密照片由另一个域名上的 Worker 通过 R2 binding 读取，这条路径不经过公开域名，所以不受 WAF 影响。

| 方案 | 结论 |
| --- | --- |
| 私密照片保持原名，和公开照片放在同一目录 | 否决。相簿名公开、相机文件名是连续编号，中间缺的编号就是私密照片，改个编号就能下载 |
| 私密照片改用随机文件名，不加访问控制 | 否决。可以防猜测，但链接永久有效，撤销要重新命名并重新上传 |
| 原名 + 随机前缀目录 | 否决。只要泄漏一条链接，前缀就暴露了，所有私密照片都能被猜出来 |
| 公开和私密各用一个桶 | 可行，配置出错时默认拦截。但要多维护一个桶，同步也要分两次 |
| 单个私有桶，所有图片都走 Worker | 否决。公开流量也会算进 Worker 的请求额度，额度用完时整站图片都会加载失败，Worker 也成了公开站点的单点 |
| **单桶 + WAF 白名单（采用）** | 公开链路完全不变；规则是白名单，根目录下误传的任何文件（`state.json`、脚本、私密文件）都会被默认拦截 |

之所以把公开照片也移到 `public/` 前缀下，就是为了让 WAF 规则可以写成白名单（“只放行 `/public/`”），而不是黑名单（“拦截 `/private/`”）。代价是公开图片的 URL 全部改变一次，访客的浏览器缓存和 CDN 缓存需要重新加载。

### 3.2 媒体鉴权：Worker + R2 binding + 签名 URL

| 方案 | 结论 |
| --- | --- |
| **Worker 校验 HMAC 签名（采用）** | 可以用自定义域名；用 Cache API 做边缘缓存；Worker 不需要知道密码；按个人使用量算不收费 |
| R2 预签名 URL（S3 API） | 不需要 Worker，但只能用 `r2.cloudflarestorage.com` 域名，没有 CDN 缓存，Vercel 还要保存 S3 密钥 |
| 公开域名 + WAF 的 HMAC 校验规则 | 需要 Pro 套餐；而且规则一旦关闭就等于全部公开 |
| 用 cookie 鉴权 | 要把 cookie 设到 `.shiyu.me` 下，跨子域请求还要带凭据、改 CORS，前端的 `fetch` 也要跟着改 |

签名的过期时间直接取解锁会话的过期时间，所以同一次会话里每张图片的 URL 不变，浏览器缓存照样有效。

### 3.3 页面：服务端合并 + proxy rewrite 到 `/vault`

| 方案 | 结论 |
| --- | --- |
| **proxy 按 cookie 把请求 rewrite 到 `/vault` 动态变体，在服务端合并两份 manifest（采用）** | 公开访客的路径一行不改。组件不用改，只是传入的照片列表里多了私密照片。URL 也保持不变 |
| 页面保持公开版本，解锁后在前端拼装私密照片 | 否决。相簿时间线、相簿页、地图的分组都是服务端计算的，只有私密照片的相簿页和 `/photos/<私密 slug>` 在静态产物里都是 404，这些都要在前端重写一遍 |
| 所有页面都改成读 cookie 的动态渲染 | 否决。公开访客会失去静态缓存，首页 HTML 有 860 KB，每次请求都要重新渲染 |
| 不用 proxy，解锁后直接访问 `/vault/...` | 否决。站内所有链接和 Viewer 写入的 URL 都要加前缀，私密模式下复制的链接也和公开链接不一样 |

### 3.4 密码只在服务端校验

密码和它的哈希都不能出现在前端代码里：前端代码谁都能下载，可以离线暴力破解，私密 manifest 的地址也会跟着暴露。所以只有服务端知道密码，Worker 也不知道。

## 4. Pipeline（已实施）

配置见 [pipeline.toml.example](../../pipeline/pipeline.toml.example)，所有键统一用 snake_case：

```toml
source_path = "/Volumes/Xin T7/Photography"
target_path = "/Volumes/Xin T7/R2"
# originals_dir、thumbnails_dir 和编码参数不变

[public]
dir = "public"
tags = ["XIN"]

[private]
dir = "private"
tags = ["YUN"]
```

- **怎么分类**：带私密标签的照片进私密目录；否则带公开标签的进公开目录（`public.tags = []` 表示所有没有私密标签的照片都公开）；两种都不带的不参与构建。**同时带两种标签时按私密处理**，并给出警告，这样标错的时候默认不会泄漏。
- **配置校验**：配置文件里出现未知的键会直接报错，避免旧的 `sourceTags` 被悄悄忽略；同一个标签不能同时出现在两边；两个目录名不能相同（不区分大小写，因为 APFS 不区分大小写，而 R2 区分）。
- **输出**：每个目录下都有 `gallery/`、`thumbnails/` 和 `manifest.json`。manifest 里的路径都相对于各自的目录（`gallery/<相簿>/<文件>.avif`）。Web 按父目录名判断相簿，所以私密照片和同一文件夹里的公开照片会自然归到同一个相簿。
- **唯一性**：两个目录的 manifest 路径加在一起必须唯一，否则构建失败（Web 用这个路径作为照片 id）；文件名重复会给出警告（文件名就是页面 slug）。
- **切换公开/私密时**：已有的图片文件直接移动到另一个目录，不重新编码。旧目录里多余的输出由清理逻辑删除，两个目录都会被清理。
- **`state.json`**：只有一份，放在 `target_path` 根目录。它列出了所有源文件（包括私密照片），**只保留在本地**。

## 5. R2 目录与同步（已实施）

```text
/Volumes/Xin T7/R2/                    R2 桶 gallery/
  public/                        →       public/
    manifest.json  map.json                manifest.json  map.json
    gallery/  thumbnails/                  gallery/  thumbnails/
  private/                       →       private/
    manifest.json                          manifest.json
    gallery/  thumbnails/                  gallery/  thumbnails/
  build.sh  sync_r2.sh           →       build.sh  sync_r2.sh   （上传了，但会被 WAF 拦截）
  state.json  .r2-sync/                  （不上传）
```

`map.json` 是相簿坐标，公开和私密照片共用一份，所以放在 `public/` 下。

`sync_r2.sh` 放在 R2 目录里，不在仓库中。它有两种模式：

| 模式 | 行为 |
| --- | --- |
| `./sync_r2.sh`（fast，默认） | 和上次的快照对比，上传新增或修改的文件，**并删除远端上本地已经移除的文件** |
| `./sync_r2.sh full` | 完整镜像，删除远端多余的文件和被排除的文件 |
| 加 `--dry-run` | 只预览，可以和上面两种一起用 |

这次修改的内容：

- 加入删除逻辑。原来 fast 模式只上传不删除，照片改为私密后，`public/` 下的旧文件会一直留在 R2 上；远端多出来的 4 张 Malta 旧照片就是这么来的。
- 不再上传 `state.json` 和构建过程中的临时文件；full 模式会顺带删掉远端已有的 `state.json`。
- 删除 `public/` 下的文件后，列出对应的 URL，提醒去 CDN 清除缓存；如果设置了 `CLOUDFLARE_ZONE_ID` 和 `CLOUDFLARE_API_TOKEN`，会自动清除。照片从公开改为私密时，这一步必须做。
- 加了 `--s3-no-check-bucket`。原来 fast 模式的增量上传会因为令牌没有建桶权限而失败（403）。

迁移时，远端已有的图片是用 `rclone move` 在服务端直接移动到 `public/` 下的，没有重新上传那 4.7 GB。

## 6. 公开域名的 WAF（已实施）

在 Cloudflare 的 Security → WAF → Custom rules 里配置，动作是 Block：

```text
(http.host eq "cloud.shiyu.me" and not starts_with(http.request.uri.path, "/public/"))
```

R2 桶的 Public Development URL（`r2.dev`）已关闭，自定义域名只有 `cloud.shiyu.me` 一个。

GET 实测结果（2026-10-22）：

| 请求 | 结果 |
| --- | --- |
| `/public/manifest.json`、`/public/map.json`、`/public/thumbnails/…` | 200 |
| `/private/manifest.json`、`/private/gallery/…`、`/private/thumbnails/…` | 403 |
| `/state.json`、`/sync_r2.sh`、`/build.sh`、`/` | 403 |
| `/public/../private/…`、`/public/%2E%2E/private/…`、`/public//../private/…`、`/public/./../private/…` | 403 |
| `/Private/…`、`/%70rivate/…`、`//private/…`、查询参数里带 `/public/`、大写域名、末尾带点的域名 | 403 |
| `/public/..%2Fprivate/…` | 能通过 WAF，但 R2 把它当成字面上的对象名，返回 404，没有泄漏 |

WAF 在 CDN 缓存之前执行，所以已经被缓存的私密文件也会被拦截。

## 7. 私密媒体 Worker（已实现，待部署）

代码在 [worker/src/index.ts](../../worker/src/index.ts)，配置在 [worker/wrangler.jsonc](../../worker/wrangler.jsonc)，部署步骤见 [worker/README.md](../../worker/README.md)。

- 域名是 `private.shiyu.me`（Worker 自定义域名）。`workers.dev` 和预览地址都关闭了，只有这一个入口。
- R2 binding `MEDIA_BUCKET` 指向 `gallery` 桶，代码只读 `private/` 前缀下的文件，并且只接受 `gallery/` 和 `thumbnails/` 开头的路径。

| 请求 | 校验 | 返回 |
| --- | --- | --- |
| `GET /<assetPath>?exp=…&sig=…` | `sig = base64url(HMAC-SHA256(MEDIA_SIGNING_SECRET, "${exp}:${assetPath}"))`，`exp` 必须是未来的时间且不超过 7 天 | 图片，`Cache-Control: private, max-age=<离 exp 剩余的秒数>` |
| `GET /manifest.json` + `Authorization: Bearer <PRIVATE_MANIFEST_TOKEN>` | 先算 SHA-256，再做固定时间比较 | 私密 manifest，`no-store` |
| 其他所有请求 | — | 统一返回 404，不透露文件是否存在 |

- `assetPath` 就是私密 manifest 里的路径，签名时不带开头的 `/`。
- 签名校验通过后，以不带查询参数的路径作为缓存键查 Cache API，没有再读 R2；每个数据中心缓存 30 天。所以同名重新导出的私密图片，最多 30 天内仍可能返回旧版本。
- `ALLOWED_ORIGINS`（`https://gallery.shiyu.me`、`http://localhost:3000`）决定 CORS：Viewer 加载原图和下载时用的是 `fetch`，需要这个头。用 `<img>` 显示不受影响。
- 支持 HEAD 请求和 `If-None-Match`（返回 304）。

本地 `wrangler dev` 测了 21 种请求，结果都符合预期：

- 正常请求：200 和 304 的情况、CORS 只对允许的来源返回。
- 被拒绝的请求，全部返回 404：签名错误、签名用于别的文件、篡改 `exp`、已过期、`exp` 超过 7 天、路径穿越、访问目录以外的路径、令牌错误、POST 请求。

费用：按个人访问量，Workers 的免费额度（每天 10 万次请求）足够用。超出时只是私密图片加载失败，不会扣费，公开站点也不受影响。

## 8. 密钥

| 名称 | 作用 | 存放位置 |
| --- | --- | --- |
| `PRIVATE_ACCESS_PASSWORD`（名称暂定） | 你在前端输入的密码 | 只在 Vercel |
| `PRIVATE_SESSION_SECRET` | 给解锁 cookie 签名 | 只在 Vercel |
| `MEDIA_SIGNING_SECRET` | 生成和校验私密图片 URL 的签名 | Vercel 和 Worker，值相同 |
| `PRIVATE_MANIFEST_TOKEN` | 服务端拉取私密 manifest 时证明身份 | Vercel 和 Worker，值相同 |

```text
输入密码 ──→ Next.js 校验 PRIVATE_ACCESS_PASSWORD
              └─ 发 cookie，用 PRIVATE_SESSION_SECRET 签名
请求页面 ──→ Next.js 校验 cookie
              ├─ 用 PRIVATE_MANIFEST_TOKEN 向 Worker 拉取私密 manifest
              └─ 用 MEDIA_SIGNING_SECRET 给私密图片 URL 签名
加载图片 ──→ Worker 用 MEDIA_SIGNING_SECRET 校验签名 → 返回 R2 中的文件
```

- 后三个都是机器之间用的，用 `openssl rand -base64 32` 生成，存在密码管理器里，不进仓库。
- 密码由你自己设置。暴力破解靠服务端限流来防。
- 轮换的影响：
  - 改密码：所有已解锁的设备都失效（cookie 签名里带了密码的哈希）。
  - 换 `PRIVATE_SESSION_SECRET`：效果相同。
  - 换 `MEDIA_SIGNING_SECRET`：所有已签发的图片链接失效，Worker 和 Vercel 两边要一起改。

## 9. 前端私密模式（待实施）

### 9.1 解锁与会话

- **解锁入口**：还没定。可以在 Header 里放一个锁图标，或者用一个隐藏入口（不放任何链接的 `/unlock` 路由，或者一个快捷键）。在 Header 放锁图标，相当于告诉所有访客这里有隐私内容。
- **校验**：通过 Server Action 提交。服务端对密码的 SHA-256 做 `timingSafeEqual` 比较，失败时统一延迟一段时间再返回。在 Vercel Firewall 里给这个路径加一条限流规则。
- **cookie 格式**：`<exp>.<sig>`，其中 `sig = HMAC(PRIVATE_SESSION_SECRET, exp + SHA-256(密码))`。服务端不保存任何状态。
- **cookie 属性**：`HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=259200`（3 天），只对 `gallery.shiyu.me` 生效。有效期固定，不随访问续期。
- **锁定**：清除 cookie。解锁或锁定之后都执行一次 `location.reload()`，清掉客户端路由缓存里另一个变体的页面数据。

### 9.2 proxy 与 `/vault` 变体

- `web/proxy.ts`：matcher 只匹配页面路由（排除 `_next`、`vault`、`api` 和静态资源），并设置 `has: [{ type: 'cookie', key: <cookie 名> }]`。这样没有 cookie 的公开访客请求时，proxy 根本不运行。cookie 有效时 rewrite 到 `/vault<pathname>`，无效或过期时原样放行。
- `web/app/vault/`：几个很薄的页面，复用现有组件。每个页面都显式声明 `export const dynamic = 'force-dynamic'`，**并且在页面里再校验一次 cookie**：即使绕过 proxy、直接访问 `/vault/*`，也只会得到 404。
- Header 里的照片数量在根 layout 中，拿不到当前是哪个变体：要么把 Header 移到各变体自己的 layout 里，要么接受它一直显示公开照片的数量。
- 这一步要新建 `app/vault/` 和 `proxy.ts`，现有的路由文件不需要移动。

### 9.3 数据层

- 新增服务端专用的 `getPrivatePhotoCollection()`：带 Bearer 令牌拉取 `https://private.shiyu.me/manifest.json`，和公开 manifest 合并后按 `takenAt` 排序。私密照片多一个 `visibility: 'private'` 字段，图片 URL 换成签名 URL（`exp` 取会话的过期时间）。
- `getAlbumCatalog` 和 `map-items` 改为能接收不同的数据源。两边的相簿 key 都取父目录名，所以照片会自然合并到同一个相簿和同一个地图点。
- 私密 manifest 只在服务端读取，可以放进 Next 的数据缓存（只在服务端）；页面的渲染结果绝不能缓存。

### 9.4 UI 与分享

- 私密照片在 Viewer 和瀑布流里显示一个小锁标记。
- 分享弹窗：保留“复制链接”，加一句提示“仅解锁设备可访问”；隐藏 Twitter 和 Telegram（对方打开是 404，也没有预览图）；下载照常可用（走签名 URL）。
- 私密照片的 OG 图对爬虫返回 404。
- 第二期（可选）：临时分享链接 `/s/<token>`，token 由 slug 和过期时间签名生成。对方只能看到这一张照片，看不到相簿和其他私密照片。

### 9.5 费用

只有带 cookie 的请求才会运行 proxy 和动态渲染，也就是只有你自己，所以 Vercel 上新增的调用次数可以忽略。如果去掉 `has` 条件，或者 matcher 写得太宽，proxy 就会对每个访客的每次请求都运行。

## 12. 已知问题与后续

- 即使内容没变，`public/manifest.json` 每次构建都会被重写、`updatedAt` 都会变（原因推断是 `f32` 字段在比较时精度不一致，这个问题在这次改动之前就存在），所以每次同步都会重新上传 520 KB 的 manifest。
- 公开图片旧路径（`/gallery/…`、`/thumbnails/…`）还留在 CDN 边缘缓存里。它们都是公开照片，没有风险，会自然过期。
- 可以在 `sync_r2.sh` 里加一道保护：同步前用 GET 请求 `cloud.shiyu.me/private/manifest.json`，如果返回 200 就拒绝上传 `private/`。这样 WAF 规则即使丢失也不会泄漏。
- 本地运行 Worker 时新建了 `.claude/launch.json`，这个文件不需要提交。
