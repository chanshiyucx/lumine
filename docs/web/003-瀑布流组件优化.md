# 瀑布流组件优化

组件路径：`components/photo/photo-masonry.tsx`

## 背景

首页视觉经过前两轮调整后，瀑布流的观感已经接近目标，但组件内部仍然存在一些结构问题：

1. `PhotoCard` 内联在 `PhotoMasonry` 文件里，文件职责过重，不利于维护
2. 当前组件对外 props 过宽，Server Component 把未使用的数据也传进了客户端
3. 文档里提到的交互能力需要重新确认，尤其是点击图片打开预览
4. 是否应该将 `img` 替换为 `next/image`，需要给出明确结论

这次优化的目标不是再大改视觉，而是把瀑布流组件本身整理成更合理、可维护的形态。

## 结论

### 1. 需要将 `img` 替换为 `next/image` 吗？

当前结论：**首页瀑布流没有必要强制切到 `next/image`，继续保留 `img` 更合适。**

原因如下：

1. 首页缩略图已经是预生成的 `webp thumbnail`，并不是未经优化的大图原件
2. 缩略图来自外部 R2 域名，切到 `next/image` 后还要继续维护 remote pattern、loader 行为和图片优化路径
3. 首页瀑布流是高密度图片列表，使用原生 `img` 更接近参考实现，也能保持更轻的 DOM 结构
4. 当前卡片需要双图层过渡：
   底层 `blurDataUrl`
   顶层 `thumbnail`
   用 `img` 实现这套过渡更直接，也更方便处理缓存命中和 `onLoad` 时序问题
5. `next/image` 真正更有价值的场景通常是：
   首屏核心 hero 图
   需要自动尺寸推断与 `srcset`
   需要内建图片优化链路
   当前首页瀑布流不属于这几类高收益场景

也就是说，这里不是不能用 `next/image`，而是 **收益不大，复杂度会变高，且不符合当前首页“更贴近 Afilmory、DOM 更轻”的方向。**

### 2. 是否有必要拆出 `PhotoCard`？

有必要，而且已经执行。

原因：

1. `PhotoMasonry` 原文件同时承担了：
   布局计算
   列分配
   卡片 hover 视觉
   图片加载状态
   键盘交互
2. 这会让瀑布流布局逻辑和单卡片视觉逻辑耦合在一起
3. 后续只要调整 hover、标签、占位图、元信息展示，都必须在同一个大文件里修改

## 已实施修复

### 1. `PhotoCard` 拆成单独组件

新增文件：

- `components/photo/photo-card.tsx`

现在 `PhotoCard` 独立负责：

- 缩略图加载状态
- blur 占位与双 `img` 结构
- hover 缩放和信息层
- 键盘可访问性
- 点击打开回调

而 `PhotoMasonry` 回归为：

- 监听容器宽度
- 计算列数/列宽
- 分配瀑布流列
- 管理当前打开的预览索引

### 2. 瀑布流辅助逻辑抽离

新增文件：

- `components/photo/photo-masonry.utils.ts`

当前被抽出的内容包括：

- `PositionedPhoto` 类型
- `formatBytes`
- `formatMimeLabel`
- `formatAlbumChip`
- `getColumnConfig`

这样后续如果继续调：

- 列宽策略
- 标签展示
- hover 元信息

都不必再去碰主组件文件的大块 JSX。

### 3. 恢复点击图片打开预览

这次检查里发现一个实际功能回归：

- `PhotoMasonry` 里的 `PhotoCard` 点击逻辑被注释掉了
- `PhotoViewer` 虽然还存在，但没有重新接回首页

这个问题已经修复：

- `PhotoMasonry` 新增 `activeIndex`
- 点击任意卡片会设置当前索引
- `PhotoViewer` 重新挂回瀑布流页面
- 支持关闭、切换、同步更新索引

这不是单纯的结构优化，而是实际恢复了首页预览能力。

### 4. 收窄 Client Component 的 props

根据 Next App Router 的 Server/Client 组件边界原则，客户端组件应该只接收真正需要的序列化数据。

此前：

- `app/page.tsx` 直接把整个 `photoCollection` 展开传给 `PhotoMasonry`
- 但 `PhotoMasonry` 实际只使用了 `photos`

现在已经改为：

- `app/page.tsx` 只传 `photos={photoCollection.photos}`

收益：

1. 降低 Server Component 到 Client Component 的无效数据传输
2. 减少组件接口噪音
3. 明确 `PhotoMasonry` 的真实职责是“渲染图片墙”，而不是消费整份页面元数据

### 5. hover 交互保留，但不再继续加重

当前 hover 参数仍然维持在更接近 Afilmory 的值：

- `duration-300`
- `ease-out`
- `group-hover:scale-105`

这个方案继续保留，不再额外引入更重的动画库或更复杂的过渡层。

## 当前设计还存在哪些不足？

结合当前实现和 Afilmory 参考实现，仍有几个可以继续优化的点。

### 1. 还没有做虚拟化

当前瀑布流会一次性把所有图片卡片都渲染出来。

这在 30~100 张图时问题不大，但如果照片数量继续增加，会出现：

- 首屏 DOM 体积变大
- 图片观察和 hover 事件变多
- 客户端重排成本上升

后续可以考虑：

- 引入窗口化 / 虚拟化
- 或改成绝对定位瀑布流并按可视区域增量渲染

### 2. 列布局算法仍然是“客户端计算”

当前做法是：

- 先渲染空容器
- 等 `ResizeObserver` 拿到宽度后再计算列布局

这简单有效，但也意味着：

- 首次 hydration 后才得到最终列结构
- 宽度变化会触发重新分列

如果后面需要更强的稳定性，可以进一步优化：

1. 给容器宽度建立更稳定的断点策略
2. 在服务端预估首屏列配置
3. 或者引入更成熟的 masonry 布局抽象

### 3. 预览层还没有和 URL 同步

现在点击卡片能打开 `PhotoViewer`，但仍然只是前端状态：

- 刷新后预览关闭
- 无法分享某一张图的深链接

这点在文档 `001` 中也提过，后续最值得补的是：

- `?photo=xxx`
- 或 hash / route segment 同步

### 4. 卡片元信息还是“前端拼接文案”

当前 `PhotoCard` 里的元信息是运行时拼接：

- 文件格式
- 分辨率
- 文件大小
- album chip

这已经够用，但如果后续 metadata 继续变复杂，建议往数据层推进：

- 在 `lib/photos.ts` 里直接生成展示态字段
- 让 UI 组件只负责渲染，不再自己拼接展示文案

## 后续建议

如果继续沿这个方向迭代，我建议按下面顺序：

1. 给 `PhotoViewer` 加 URL 同步
2. 给瀑布流做虚拟化或按需渲染
3. 把展示态 metadata 进一步下沉到 `lib/photos.ts`
4. 如果图片数量继续增大，再重新评估是否需要 `next/image` 或自定义 loader
