# 首页瀑布流前端性能与规范优化

- 日期：2026-10-19
- 状态：第 3 节各项已实施，未提交。没有做移动真机测试和弱网 LCP 对比
- 范围：`web/app/page.tsx`、`web/components/gallery/`、`web/components/image/image-preloads.tsx`、`web/components/image/thumbnail-image.tsx`
- 证据口径：当前源码、已安装的 `@tanstack/virtual-core@3.17.10` 和 `tailwindcss` 源码、线上首页和 manifest，以及本机 `next start` 生产构建在桌面 Chromium 中的实测。实测之外的结论标为“推断”或“待测”。

## 1. 结论

瀑布流只有一条渲染路径；`estimateSize` 按宽高比给出精确高度，不需要测量 DOM；卡片用绝对定位，正常滚动时位置不变。TanStack 的滚动通知主要由可见范围和滚动状态变化触发，焦点、布局和悬停能力变化也会引起更新。目前没有证据支持重构虚拟列表、滚动容器或数据流，也没有测量证明 React 渲染是主要瓶颈。

这次只做前端范围内能确认收益、改动小的几项：

1. 首屏前 2 张缩略图的预加载链接随首屏 HTML 输出，不再等 hydration 之后才发现。
2. 不支持悬停的设备不再渲染悬停信息层。
3. 虚拟列表补上序号语义，键盘焦点所在的卡片不会因为滚出范围而被卸载。
4. 给 `measure()` 补注释，说明它为什么不能删。

## 3. 已实施

### 3.1 首屏前 2 张缩略图随 HTML 预加载

**问题。**瀑布流要在客户端拿到滚动元素、测出容器宽度后才启用虚拟列表，所以服务端 HTML 里没有任何 `<img>`。前 `3 × 列数` 张虽然设了 `loading="eager"`，但图片节点本身就是 hydration 之后才创建的，浏览器的预加载扫描器无法提前发现它们。Next 16 的 `<Image preload>` 在这里也不起作用，因为图片只在客户端渲染，插入预加载链接时已经晚了。

**做法。**

- [首页](../../web/app/page.tsx)只向 [ImagePreloads](../../web/components/image/image-preloads.tsx) 传递前 `PRIORITY_PHOTO_COUNT` 张缩略图的 URL。
- `ImagePreloads` 是一个返回 `null` 的 Client Component，在渲染中调用 `react-dom` 的 `preload(url, { as: 'image', fetchPriority: 'high' })`。它仍参与首次 SSR，所以初始 HTML 的 `<head>` 中会有预加载链接；不需要等 hydration 或 effect。
- [瀑布流](../../web/components/gallery/photo-masonry.tsx)给同样这几张卡片设置 `fetchPriority="high"`。[ThumbnailImage](../../web/components/image/thumbnail-image.tsx)为此新增可选的 `fetchPriority` 参数。
- 是否提高优先级由 [PhotoGallery](../../web/components/gallery/photo-gallery.tsx) 根据页面入口决定，通过 `prioritizeFirstPhotos` 传给瀑布流；瀑布流只负责“提高哪几张”。
- `PRIORITY_PHOTO_COUNT = 2` 定义在 [masonry-layout.ts](../../web/components/gallery/lib/masonry-layout.ts)，并通过 `components/gallery/index.ts` 导出给页面使用。容器宽度至少 320px 时，多列布局的前两张都在第一行；不足 320px 的单列兜底会预加载前两行，不保证两张都在首屏。

**为什么只取 2 张。**预加载的图片如果首屏用不到，就是在和真正需要的资源抢带宽；只取 2 张可以限制提前加载的资源量，覆盖常规多列布局的两张首行图片。前 `3 × 列数` 张的 `eager` 保持不变。

**为什么需要 Client Component 边界。**直接在 Server Component 的 `page.tsx` 中调用 `preload`，会把立即执行的图片提示写入 RSC 响应。照片直达页的 Header 自动预取首页时，也会解析这些提示，导致 Viewer 尚在显示其他照片时，首页前两张图就被声明为高优先级。仅取消背景 `<img>` 的 `fetchPriority` 不能阻止这条路径。`ImagePreloads` 在路由预取时只作为组件引用和两条 URL 被序列化，不执行其渲染；首次 SSR 或实际导航到首页时才产生图片预加载提示。使用方式与 Next.js 的 [Resource hints](https://nextjs.org/docs/app/api-reference/functions/generate-metadata#resource-hints) 文档一致。

**为什么放在 `components/image/`。**`app/` 下除路由文件外只放以 `_` 开头的私有模块（如 `_data.ts`）。这个组件只接收一组图片 URL，与照片业务无关，属于底层图片能力，所以按 [035 号文档](035-底层图片组件集中与缩略图复用.md)的职责划分放在 `components/image/`，命名为 `ImagePreloads`，从 `@/components/image` 导出。

**没有做的。**没有恢复服务端临时布局。[014 号文档](014-瀑布流优化v2.md)已经说明，首帧和最终帧使用两套布局会导致列数错误、空位和跳动。预加载只改变下载的起始时间，不改变渲染路径。

**此前实测（调整预加载边界前，本机生产构建，桌面 Chromium，无网络限速）。**

- 预渲染的 `index.html` 中有两条 `<link rel="preload" as="image" fetchPriority="high">`。
- 这 2 张图在页面开始后约 102 ms 开始下载，与 JS、CSS 同时发起；其余缩略图约 302 ms 才开始。
- 每张预加载的图只有一条请求记录，说明 `<img>` 复用了预加载结果，没有重复下载。
- 控制台没有出现图片“已预加载但未使用”的警告。

本机无限速时 LCP 约 424 ms，没有改动前在同等条件下的对照数据。弱网和移动端的实际收益**待测**，方法见第 5 节。

**调整预加载边界后的回归。**

- Node 24 生产构建的首页 HTML 仍有两条高优先级图片预加载链接；首页 RSC 产物不再包含图片 `:HL` 指令。
- 对首页和 `/photos/DSC09106` 分别发送普通 GET 与带 `RSC: 1`、`Next-Router-Prefetch: 1` 的 GET：只有首页 HTML 有两条图片预加载链接，两条路由的 RSC 响应均无立即执行的图片提示。
- 在新开的照片直达页中，资源记录确认 Header 已预取首页；此时 DOM 中的图片 preload 数和背景列表的 `fetchpriority` 属性数均为 0。
- 关闭 Viewer 后实际点击 Home，页面才新增两条高优先级图片预加载链接，首两张卡片也具有 `fetchpriority="high"`。

**影响范围。**只有首页实际渲染 `ImagePreloads`，首页路由预取不执行它。

- 相册页：前 2 张卡片带 `fetchPriority="high"`，但页面没有渲染 `ImagePreloads`，相册页的收益还没评估。
- 照片直达页（`/photos/[photoId]`）：`initialPhotoSlug` 存在时，`prioritizeFirstPhotos` 为 `false`。prop 不用 `initial` 命名，是为了避免和表示直达照片的 `initialPhotoSlug` 混淆。这类页面首先显示的是 Viewer 里的那张照片，背景列表前两张往往是别的照片，不应和 Viewer 争抢带宽。首页的路由预取也不会为它们添加图片预加载提示。背景列表既有的 eager 加载行为不在本次修改范围内。

### 3.2 不支持悬停的设备不渲染悬停信息层

**问题。**每张卡片都会挂载标题、格式和尺寸行、相册标签以及 4 个拍摄参数，并调用 `getCaptureSettings` 和 `formatBytes`。Tailwind v4 的 `hover`/`group-hover` 会被包在 `@media (hover: hover)` 里，在 `tailwindcss` 源码中可以确认。所以在不支持悬停的输入环境里，这一层不会显示，却一直占着 DOM。判断依据是输入能力，不是设备是否有触屏。

**做法。**[PhotoMasonry](../../web/components/gallery/photo-masonry.tsx)用 `useMediaQuery('(hover: hover)')` 订阅一次结果，再以 `showHoverInfo` 传给所有卡片；[PhotoMasonryItem](../../web/components/gallery/photo-masonry-item.tsx)只在条件为真时渲染这一层，拍摄参数也只在这时计算。之所以由列表统一订阅，是为了避免每张卡片各自订阅媒体查询。

按钮的可访问名称来自 `aria-label`，不依赖这一层文字，所以读屏输出不变。卡片要等布局测量完才挂载，晚于 hydration，因此服务端快照返回 `false` 不会引起 hydration 不一致。

**实测。**在桌面上，一张高于 140 px 的卡片有 38 个 DOM 节点；在移动端模拟（375 × 812，`hover: none`）下每张卡片只有 5 个节点。桌面悬停仍会正常显示标题、相册标签和拍摄参数。

收益体现在快速滚动时每次挂载新卡片的成本上，真机滚动帧时间的变化**待测**。

**没有改的。**悬停时每张卡片有多个独立的透明度过渡，这是有意为之：父元素透明度小于 1 时，子元素的 `backdrop-filter` 只能模糊父元素内部的内容，模糊不到下面的照片。所以不能把透明度合并到父元素上。

### 3.3 虚拟列表的序号语义与键盘焦点保留

**问题。**

1. 虚拟列表同时只挂载几十个 `<li>`，读屏软件无法知道这是“第几张 / 共几张”。
2. 用键盘把焦点移到某张卡片后，只要滚动让它离开范围，卡片就会被卸载，焦点随之掉到 `body` 上，Tab 顺序中断。

**做法。**

- 每个 `<li>` 加上 `aria-posinset={index + 1}` 和 `aria-setsize={photos.length}`。
- 列表在 `<ul>` 上监听 `onFocus`/`onBlur`，记录获得焦点的卡片序号，再通过 TanStack 的 `rangeExtractor` 把**这张卡片及其前后各一张**追加到渲染范围里，按序号排序以保持 DOM 和 Tab 顺序。焦点离开列表后清除记录，这几张卡片会在下一次范围变化时正常卸载。
- 所有获得焦点的情况都会记录，不区分键盘还是鼠标。

**评审后的两处修正。**第一版有两个已复现的问题：

1. **只记录 `:focus-visible` 的焦点。**原意是避免鼠标点击打开 Viewer 时重新渲染列表，但这样会漏掉程序设置的焦点。实测：用鼠标点开 Viewer、再点关闭按钮后，焦点被恢复到原卡片，此时不匹配 `:focus-visible`，所以没有被记录；滚走后卡片被卸载，焦点掉到 `body`。而且原先想省的那次渲染也不在转场的关键时刻：按钮在 `mousedown` 时获得焦点，早于 `click` 触发打开；列表卡片都有 `memo`，这次重新渲染不会产生 DOM 变化。因此去掉了这个判断。
2. **只保留焦点卡片本身。**Tab 会跳到当前渲染范围里的第一张卡片，而不是下一张；Shift+Tab 则会直接跳出列表，因为前一张没有挂载。保留前后相邻的两张后，Tab / Shift+Tab 能到达相邻卡片，浏览器会把它滚入视口，渲染范围随之移过来。

**为什么用 state 而不是 ref。**TanStack 只在 `rangeExtractor`、`overscan`、`count` 或起止序号变化时才重新计算渲染范围（见 `getVirtualIndexes` 的缓存依赖）。用 state 时，焦点变化会生成新的 `rangeExtractor`，范围随之重新计算，不需要在渲染过程中读取 ref。

计算顶部 Header 当前相册时，这几张保留的卡片在视口外，与视口的交叠高度为 0，会被 `getDominantMasonryPhoto` 跳过，不影响结果。

**实测。**

- 用鼠标点击 1 号卡片打开 Viewer，再点关闭按钮，焦点回到 1 号卡片；把页面滚动到 8000 px 后，渲染序号为 `[0, 1, 2, 164, 165, …]`，焦点仍在 1 号卡片上，序号保持升序。
- 此时按 Tab，焦点移到 2 号，页面滚回顶部；再连按两次 Shift+Tab，焦点依次回到 1 号和 0 号。
- 照片直达页 `/photos/DSC09106` 的背景列表没有 `fetchpriority`；首页前 2 张为 `high`。首页预加载与路由预取的隔离见 3.1 节。

### 3.4 `measure()` 的注释

TanStack 计算布局时的缓存依赖包括 `count`、`gap`、`lanes`、`scrollMargin`、`getItemKey` 等，但不包括 `estimateSize`。列数不变而列宽变化时，必须主动调用 `virtualizer.measure()` 重新计算布局。这个 layout effect 看起来像是可以删掉的冗余代码，所以补了注释说明原因。

## 4. 评估后决定不做

### 4.1 去掉 `useGalleryHeader` 里手写的 `useCallback`

原先的想法是：这个 hook 会被 React Compiler 编译，手写缓存与 [034 号文档](034-首页图片链路与瀑布流更新边界清理.md)“不与编译器重复维护依赖”的原则不一致。

实际试着去掉之后，`publishHeader` 作为 `useEffect` 的依赖，触发了 `react-hooks/exhaustive-deps` 警告。这个规则不知道编译器的存在，会要求稳定的函数引用。如果改用 `useEffectEvent`，返回给瀑布流的回调又是在 effect 之外调用的，不符合 Effect Event 的使用约束；而且 `fixedHeaderDetail` 变化时也不会重新发布。因此保留 `useCallback`。

034 号文档撤掉的是 Viewer 控制器中不作为 effect 依赖的缓存，两种情况不同。

### 4.2 把 Header 的 `inert` 改为订阅 store

[PhotoGallery](../../web/components/gallery/photo-gallery.tsx) 用 `querySelector('[data-site-header]')` 设置 Header 的 `inert`，属于跨组件直接操作 DOM。但 `Header` 是服务端组件，里面包含异步服务端组件 `PhotoCount`；要让 `<header>` 订阅 store，就得新增一个客户端外壳组件，把服务端内容作为 children 传进去。这会改变 Header 的组件结构，而收益只是依赖关系更清楚，行为和性能都不变。因此维持现状，留待以后调整 Header 时一并处理。

### 4.3 其他维持现状的项

- **Viewer 关闭时瀑布流滚到当前照片**：这是交互取向问题，不是缺陷。保留原列表位置同样有价值；实现上要等虚拟卡片挂载，还要协调 Viewer 的滚动锁、转场和焦点恢复。需要时单独评估。
- **Header 的 LinearBlur**（7 层 `backdrop-filter`，最大 60 px）：没有帧时间数据。真机出现滚动掉帧时再测。
- **打开 Viewer 时整棵瀑布流设为 `inert`**：它负责模态窗口的交互隔离，性能影响没有证据。
- **ThumbHash 缓存和占位图卸载**：Node 下每张约 120 µs，不能直接推算手机上的开销；以每次范围变化新挂载的卡片数估算，收益不明显。
- **滚动阈值监听改用 IntersectionObserver**：当前监听已是 passive，store 也会过滤相同的结果，没有性能问题的证据。
- **拆分列表数据和详情数据**：860 KB 是解压后的大小，实际传输约 70 KB，不足以支持改造数据流。
- **缩略图降低压缩质量**：属于 pipeline 的范围。pipeline 判断能否复用旧缩略图时不看质量参数，而且同一 URL 有一年的浏览器缓存，必须配合带版本号的 URL 才能生效，见 053 号文档。

## 5. 验证与人工回归

已通过：`pnpm lint`、`pnpm type-check`、在 Node 24 下的 `pnpm build`，以及 `app`、`components`、`hooks`、`lib` 的 Prettier 检查。全量 Prettier 检查报告的 `components/header/lib/header-nav-state.ts` 是原有问题，与本次无关。

本机生产构建上已确认：

- 首页 HTML 有两条高优先级图片预加载链接，`<img>` 复用预加载结果；首页 RSC 产物和带 `RSC: 1`、`Next-Router-Prefetch: 1` 的首页预取响应中都没有图片 `:HL` 提示。
- 首页前 2 张卡片为 `fetchpriority="high"`；照片直达页的背景列表没有 `fetchpriority`，也没有图片预加载链接。
- `aria-posinset`/`aria-setsize` 正确；用鼠标关闭 Viewer、焦点恢复到 1 号卡片后滚远，渲染序号为 `[0, 1, 2, 164, …]`，焦点保持，Tab 到 2 号、连按两次 Shift+Tab 回到 0 号。
- 支持悬停的环境下，高于 140 px 的卡片有 38 个节点，悬停信息层正常显示；不支持悬停的移动端模拟下，每张卡片最多 5 个节点。

内置浏览器面板在后台运行时动画帧会被降速，关闭 Viewer 后焦点约 3 秒才回到卡片。如果在此之前就滚走，卡片已不在范围内，焦点会按既有逻辑落到瀑布流容器上。这是测试环境的时序造成的，不是本次改动引入的问题。

未覆盖，需要人工回归：

1. **弱网 LCP 对比。**在 Chrome DevTools 中开启 Slow 4G 和 4× CPU 降速，分别在改动前后的提交上打开首页，记录 Performance 面板中的 LCP，以及第 1 张缩略图请求的起始时间。重复 3 次以上取中位数。
2. **真机滚动。**在 iOS Safari 和安卓 Chrome 上快速滚动，观察是否有空白闪烁或掉帧。
3. **读屏。**用 VoiceOver 确认卡片会播报“第 n 项，共 527 项”。
4. **Viewer 键盘关闭。**在内置浏览器中用 Escape 关闭 Viewer 没有生效，点关闭按钮正常。本次没有改动 Viewer 的键盘处理，推断是测试工具的按键没有送达页面，但需要在常规浏览器中确认。
