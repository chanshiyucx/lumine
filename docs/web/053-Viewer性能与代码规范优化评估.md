# Viewer 性能与代码规范优化评估

- 日期：2026-10-18（同日修订两次）
- 状态：评估；4.1 已决策（接受风险，见下），4.2 已出设计但搁置（[054](054-Viewer中间尺寸预览图设计.md)），现阶段只做前端的性能与代码优化（4.3、4.4）
- 范围：`web/components/viewer`、图片资源的缓存与更新策略、`docs/web` 中与 Viewer 相关的决策文档
- 证据口径：基于当前源码、已安装依赖的实现、pipeline 源码、线上 manifest 与资源响应，以及桌面 Chromium 实测（见第 2 节）。实测之外的结论都标为“推断”或“待测”。没有做移动真机测试或 Performance 录制。

## 1. 结论

Viewer 的状态机、职责拆分、焦点与 inert 管理都不需要重构。流畅度和正确性上最值得处理的问题都在**图片资源层**：

1. **缓存已经生效，但更新策略和它冲突。** 线上 GET 响应带有 `Cache-Control: max-age=31536000`，Cloudflare 边缘可以命中。但 pipeline 在照片重新导出时会覆盖同一路径。在一年的浏览器缓存下，老访客可能长期看到旧图，清理 Cloudflare 边缘缓存也清不掉浏览器里的副本。这是当前第一优先级（4.1）。
2. **原图很重。** 527 张中有 515 张是 25.6 MP 的 AVIF，中位数 8.50 MB。桌面端单张下载要 1–3 s，`createImageBitmap` 解码要 0.2–0.6 s。中间尺寸（preview）值得写一份完整设计（4.2）。
3. 面板宽度动画、移动端毛玻璃、分享弹窗的 blur 动画、Swiper 过渡锁，这几项先测量再决定，现在没有改动依据。
4. 第一版报告里关于 `decode()`、焦点 effect、全面替换 `<img>` 的建议已经撤回；第一次修订里“图片没有缓存”的结论也已撤回（见第 3 节）。

## 2. 实测数据

### 2.1 资源规模（线上 manifest，2026-10-18）

| 项目                           | 数值                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 照片数                         | 527，全部为 `image/avif`                                                                         |
| 分辨率                         | 515 张为 6192 × 4128（25.6 MP；470 张横向、45 张纵向）；12 张较低，约 4032 × 2268 到 2931 × 2186 |
| 原图体积 p10 / p50 / p90 / max | 5.40 / 8.50 / 12.50 / 20.74 MB（中位数 8.11 MiB，最大 19.78 MiB）                                |
| 缩略图                         | 600 px 宽的 WebP，中位数约 85 KB                                                                 |
| manifest                       | 约 530 KB                                                                                        |

单位按十进制 MB 计。第一次修订把 MiB 的数值写成了 MB，这里已更正。

**像素缓冲估算**：25.6 MP × 4 字节（RGBA）约为 100 MB。这是按每像素 4 字节推算的像素缓冲大小，不是实测的内存占用。浏览器实际占用还取决于解码格式、GPU 上传和缓存策略。

### 2.2 缓存响应头

| 请求方式                 | `Cache-Control`    | `cf-cache-status`                  |
| ------------------------ | ------------------ | ---------------------------------- |
| GET                      | `max-age=31536000` | 预热后为 `HIT`，首次为 `MISS`      |
| HEAD                     | 无                 | `DYNAMIC`                          |
| GET 且带 `Origin` 请求头 | `max-age=31536000` | `MISS`（缓存键不同，需要单独预热） |

第一次修订是用 `curl -I`（HEAD）读取的响应头，所以误判为“没有缓存”。Cloudflare 的缓存规则只对 GET 生效，HEAD 不具有代表性。以后核查响应头一律使用 GET。

### 2.3 浏览器实测（桌面 Chromium，16 核，Mac，测试页与资源同源）

**下载与解码**（`fetch(cache: 'no-store')` 加 `createImageBitmap`，每档单次样本）：

| 体积       | 下载    | 解码（createImageBitmap） |
| ---------- | ------- | ------------------------- |
| 约 5.4 MB  | 1338 ms | 205 ms                    |
| 约 8.5 MB  | 1600 ms | 277 ms                    |
| 约 20.7 MB | 2771 ms | 580 ms                    |

`createImageBitmap` 的计时只能作为解码基线，不等于 Viewer 实际路径（Blob URL 加 `<img>` 再交给 next/image 的 `decode()`）的耗时。下载耗时会随网络变化，移动端解码预计更慢（推断，待真机测）。

**浏览器缓存复用**（默认缓存模式，连续请求两次）：

| 资源                            | 第二次请求                                          |
| ------------------------------- | --------------------------------------------------- |
| 缩略图（约 73 KB）              | `transferSize` 为 0，从浏览器缓存读取               |
| 原图（6.8 MB 和 7.5 MB 各一张） | 再次走网络，边缘 `HIT`，`transferSize` 等于完整体积 |

外部复核者在另一个浏览器环境中观察到，原图第二次请求是 `fromDiskCache: true`。两边结果都成立，说明**原图能不能留在浏览器缓存里，取决于具体浏览器的缓存容量和单个条目的大小上限，不能保证**。缩略图这种小资源可以稳定复用。

测量说明：这次实验在资源所在的源（`cloud.shiyu.me`）上执行，`transferSize` 有效。如果是跨源测量，响应没有 `Timing-Allow-Origin` 时 `transferSize` 也会读成 0，这时不能据此判断命中了缓存。

## 4. 优化项

### 4.1 P0：让一年缓存和同路径更新一致

> **决策（2026-10-18）**：照片基本不会重新导出，暂时接受同路径覆盖的风险，不实施方案 A/B。风险和规避方法（需要更新时重命名源文件）已记录在 [README](../../README.md) 第 3 节。如果以后需要频繁重新导出，再按方案 A 实施。

现状：

- 资源按一年缓存（2.2）。
- pipeline 的输出路径由“源文件相对路径 + 扩展名”生成（`pipeline/src/build/storage.rs`，`build_original_path` / `build_thumbnail_path`）。源文件状态为 `Changed` 时，会在同一路径重新生成（`pipeline/src/build.rs`，`build_photo`）。URL 里没有内容版本。
- 仓库里没有关于上传流程版本管理的证据。

风险：如果照片重新调色后导出，就会覆盖原有的原图和缩略图。看过旧版本的访客最长可能一年都看到旧图（取决于浏览器是否还保留着这个缓存条目）。清理 Cloudflare 只能更新边缘，浏览器缓存不受影响。

两种一致的做法，二选一：

| 方案                        | 做法                                                                                                                                                                                      | 代价                                                                                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 内容变化时换 URL（推荐） | pipeline 为每个 asset 记录一个短内容哈希（写入 manifest，或者直接放进文件名），Web 在 `normalizeAsset` 里生成带版本的 URL，例如 `?v=<hash>`。继续用一年缓存，有条件时可以加 `immutable`。 | 需要改 pipeline 和 manifest schema。用查询参数时，要确认 Cloudflare 的缓存键包含查询串（默认包含），R2 会忽略查询串。改名方案还要处理旧文件的清理。 |
| B. 保持 URL，缩短缓存       | 按“能接受旧图存在多久”来设置 `max-age`，例如一天；如果需要每次都检查更新，就用 `no-cache` 加上现有的 ETag。                                                                               | 每次重新验证都有一次往返；缓存时间越短，复用越少，正好违背“原图很重”时最需要缓存的目标。                                                            |

如果照片几乎不会重新导出，也可以暂时接受这个风险。但要在部署说明里写清楚：重新导出某张照片后，老访客可能看不到更新。

验收需要分成两项，不能用一个指标代替另一个：

- **浏览器缓存**：在资源同源（或带 `Timing-Allow-Origin`）的环境里，第二次请求的 `transferSize` 为 0，或者网络事件显示 `fromDiskCache`。这时读到的响应头可能是首次保存下来的 `MISS`，不代表边缘状态。
- **边缘缓存**：另外发一次真实的网络 GET 请求（禁用浏览器缓存，或用 curl 的 GET），预热后应为 `HIT`。不要用 HEAD。
- **版本化（方案 A）**：更新一张照片后，新 URL 能返回新内容，旧 URL 不再出现在 manifest 中。

### 4.2 P1：中间尺寸 preview（先出设计，再实施）

> **决策（2026-10-18）**：搁置。现阶段不改 pipeline 和图片加载流程。设计与样本实测见 [054](054-Viewer中间尺寸预览图设计.md)。以下为评估阶段的原始分析。

收益（推断）：

- 下载、解码和像素缓冲大致随像素数变化。2560 长边约 4.4 MP，是原图的六分之一左右。
- 小文件也更有可能被浏览器缓存稳定复用（2.3 中缩略图稳定命中、原图在某些环境下不命中）。
- 移动端受益最明显。

尺寸要按“舞台 × DPR”来选：

| 场景                                   | 舞台设备像素（约） | 3:2 横图 fit 所需宽度 | 2560 preview 是否足够 |
| -------------------------------------- | ------------------ | --------------------- | --------------------- |
| 手机 390 × 844，DPR 3                  | 1170 × 约 2100     | 约 1170               | 足够                  |
| MacBook 1440 × 900，DPR 2，侧栏展开    | 约 2240 × 1670     | 约 2240               | 足够                  |
| 5K 外接屏 2560 × 1440，DPR 2，侧栏展开 | 约 4480 × 2750     | 约 4130               | 不够，接近原图        |

设计文档需要回答这些问题：

1. **切换规则**：按舞台 × DPR 选择 preview 还是原图；放大超过 preview 的像素密度时再升级到原图。
2. **升级过程**：替换 `src` 时，保持 `react-zoom-pan-pinch` 的 transform、`ImageLayout.fitScale` 和倍率提示的连续性。现在的布局计算用的是原图尺寸，这一点有利。
3. **资源生命周期**：升级期间两张图同时存在时的内存峰值，以及旧 Blob URL 的释放时机。
4. **数据与发布**：manifest schema 和 zod 校验；pipeline 的增量复用；资源要先于 manifest 上线；和 4.1 的版本化方案统一处理（preview 同样存在同路径覆盖的问题）。

需要单独决策、不和 preview 绑在一起的事项：是否保留 Blob 加进度条的链路、是否预取相邻照片、150 ms 延迟的取值。

### 4.4 P3：低风险的规范清理

| 项目                     | 说明                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| key 的实际归属           | 已安装的 `swiper-react` 在虚拟模式下，会把幻灯片的 key 改写为 `virtualIndex \|\| child.key`（`swiper/swiper-react.mjs`，`renderVirtual`）。所以 `SwiperSlide key={photo.id}` 只在索引 0 时生效，其他幻灯片的身份 key 实际上是数组下标。真正按照片身份重置状态的是 `ProgressivePhoto key={photo.original.url}`，**应该保留**。`ProgressivePhoto` 内部给 `ActiveProgressivePhoto` 加的同值 key 是多余的，可以删掉。`SwiperSlide` 上的 key 可以保留（满足 lint 要求），或者加一行注释说明它会被改写。 |
| `stopPropagation()` 无效 | 分享弹窗和 Viewer 的键盘监听挂在同一个 document 上，`stopPropagation` 拦不住后者。Viewer 实际靠 `canInteract`（分享弹窗存在时为 false）和 `defaultPrevented` 隔离。可以删掉这一行，或改成注释说明。                                                                                                                                                                                                                                                                                                |
| `useMobile()` 订阅两次   | Viewer 和 ThumbnailRail 各订阅一次。收益很小，传参也有接口成本，可做可不做。                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 硬编码颜色               | 信息面板里的 `rgb(40 40 40 / 0.56)` 没有使用主题 token。                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 纯函数单测               | **不采纳**（2026-10-18，以手动体验验证为主）。原建议：`viewer-state`、`zoom-geometry`、`double-tap-recognizer`、`mobile-viewer-gesture`、`viewer-reveal-state`、`histogram-renderer` 的插值函数。                                                                                                                                                                                                                                                                                                  |

## 5. 明确不做

- 不额外增加 `img.decode()`：next/image 已经做了。
- 不全面把图片换成原生 `<img>`：沿用 035 的决定。如果 preview 改造需要动 `ZoomableImage`，再连同“decode 后回调”的行为一起评估。
- 不迁移焦点 layout effect：051 §21 有回归证据，最多补一行注释说明它覆盖布局切换。
- 暂不收拢 Viewer 中的交互布尔值：这些变量表达的是不同的权限，目前没有导致缺陷。
- 暂不把直方图挪到 pipeline 预计算：现有实现已有请求去重、50 项缓存和 240 px 的计算上限，收益偏低。

## 8. 实施记录（2026-10-18）

范围：只做前端的性能与代码优化，不改 pipeline 和图片加载流程。

### 8.1 已完成

- `ProgressivePhoto` 删除给 `ActiveProgressivePhoto` 加的同值 key。外层的 `isActive` 切换本来就会更换元素类型，`PhotoCarousel` 里 `ProgressivePhoto` 的 key 已经按照片身份重置状态。
- `PhotoCarousel` 在保留下来的 key 旁边注明：Swiper Virtual 会按下标改写幻灯片的 key，按照片重置状态的是这一层。
- 分享弹窗的 Escape 监听删除无效的 `stopPropagation()`，改为注释说明：Viewer 的键盘监听在弹窗存在期间是关闭的（`canInteract`）。
- 起草过 viewer-state、zoom-geometry 等纯函数单测，最终全部删除，不保留测试：日常以手动体验验证为主，保持代码简洁。4.4 中的单测建议不再采纳。

### 8.2 未做及原因
